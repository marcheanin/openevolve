### 1.2 Пять дефектов, которые надо закрыть до любого нового прогона

* **D1. Мёртвый воркер.** `qwen3.7-flash` — константа 0 (3 токсичных из 800). При этом он самый дорогой по output-токенам в прогоне: 541 450 против 19 193 у gemma-3 (`budget_report.json`) — он «думает» и выдаёт мусор.
* **D2. Majority ≡ AND.** С тремя бинарными голосами и одним залипшим в 0 ансамбль побитово равен `AND(gemma-3, gemma-4)`. `tie_break` не срабатывал ни разу (0 ничьих в 6 оценках), `majority ≡ median` для нечётного числа бинарных голосов ⇒ вся «аблация агрегации» была пустой. Итог: ансамбль хуже лучшего информативного воркера по recall (0.398 vs 0.687) и по mean-GBA (0.594 vs 0.735).
* **D3. Обе версии headline-метрики мертвы.** Сырой `R_worst_group` максимизируется молчанием (ALL-ZERO = 0.7273 против 0.545–0.682 у всех эволюционировавших прогонов). Класс-сбалансированный вариант использует **глобальные** веса классов, поэтому упирается в 0.2359 одинаково у ALL-ZERO, qwen, gemma-4 и всех пяти арм.
* **D4. Reward hacking через отказ.** `parse_binary` → 0, `default_label("binary")` → 0, `fail_default` → 0. На итерации 8 прогона soft_min промпт с несбалансированной скобкой уронил все 2160 вызовов и получил `R_global = 0.8847` против честного чемпиона 0.833. При `fitness=global` (арма A) он бы выиграл.
* **D5. Порог «уверенно решённых» вычислительно пуст.** `disagreement_score` делит на `rating_max − rating_min = 4` даже для бинарной задачи. Максимум разногласия трёх бинарных голосов = 2/3/4 = **0.1667 < `anchor_max_disagreement = 0.2`** ⇒ фильтр никогда не отсекает, D_anchor строится фактически только по `err == 0`.

## 2. Блок A — исправления кода

Формат: **F#. Что → Где → Как → Тест → DoD**.
Порядок обязательный: F1–F4 закрывают reward hacking и метрику, F5–F8 — снятие ансамбля, F9–F12 — данные/бюджет/гарнесс.

### F1. Fail-closed вместо «молчаливого нуля»

* **Где:** `prime/workers/ensemble.py` (`parse_binary`, `default_label`, `parallel_predict`), `prime/fitness/metrics.py`, `prime/fitness/objective.py`.
* **Как:**
  1. Ввести константу `INVALID = -1`. `default_label(label_space)` для нового кода не используется как «голос»; вместо него `parse_label` возвращает `INVALID`, если ни один паттерн не сработал (сейчас — последний найденный `0/1`, затем `0`).
  2. `parallel_predict` при исключении/таймауте кладёт `INVALID`, а не `fail_default`.
  3. `compute_metrics`: `-1` никогда не равен `y ∈ {0,1}`, поэтому автоматически считается ошибкой в обоих классах. Добавить `invalid_rate = mean(pred == -1)` и исключить `-1` из `pred_pos_rate`.
  4. `compute_fitness`: если `invalid_rate > cfg.max_invalid_rate` (дефолт **0.02**) ⇒ вернуть `fitness = -1e9`, `reject_reason = "invalid_rate"`.
  5. Обратная совместимость: старые прогоны читаются как есть; флаг `fitness.fail_closed: true` (дефолт true для новых конфигов, false для реплеев).
* **Тест:** `tests/test_fail_closed.py` — (a) кандидат с 100% отказов получает `-1e9`, а не 0.88; (b) `invalid_rate=0.01` проходит, `0.05` — нет; (c) `-1` в предсказаниях не увеличивает ни одну accuracy.
* **DoD:** воспроизвести кейс D4 из `pred_cache` итерации 8 и показать, что теперь он отвергается.

### F2. Guard от вырожденных предикторов

* **Где:** `prime/fitness/objective.py`.
* **Как:** после `compute_metrics` — если `pred_pos_rate < cfg.min_pred_pos_rate` (0.02) или `> 1 − 0.02`, то `fitness = -1e9`, `reject_reason = "degenerate"`. Логировать в `stage_trace`, чтобы видеть, сколько мутантов уходит в этот фильтр.
* **Тест:** `tests/test_degenerate_guard.py` — all-zeros и all-ones отвергаются; предиктор с `pos_rate = 0.05` проходит.
* **DoD:** прогон офлайн по сохранённым `ensemble_predictions.npy` всех пяти арм: ни один честный кандидат не должен ложно отвергаться.

### F3. Новая группа метрик: внутригрупповая сбалансированная точность (GBA)

* **Где:** `prime/fitness/metrics.py`.
* **Как:** добавить

```python
def group_balanced_accuracies(preds, gold, group_ids, min_pos=10, min_neg=10):
    """GBA_g = 0.5*(TPR_g + TNR_g). Группы с недобором ячеек не возвращаются."""
```

  и в `compute_metrics` (при `cluster_ids is not None`) заполнять:
  `cluster_gba`, `R_worst_gba` (min по identity-группам, `none` исключена),
  `R_gba_mean` (macro по 8 группам), `R_gba_none` (отдельно),
  `toxic_recall`, `specificity`, `worst_gba_group`, `gba_eligible_groups`.
  Шринкедж — тот же приём, что уже есть (`prior_weight` к grand-mean), но применяется к TPR/TNR по отдельности: `cluster_gba_shrunk`.
* **Почему именно так (замер, §1.1):** ALL-ZERO даёт ровно 0.500 в каждой группе, т.е. молчание больше не выигрывает; на валидации gemma-3 = 0.583 против ансамбля 0.400 — метрика различает то, что должна.
* **Тест:** `tests/test_gba_metric.py` — (a) ALL-ZERO ⇒ все GBA = 0.5; (b) идеальный предиктор ⇒ 1.0; (c) группа с `pos < min_pos` не попадает в `R_worst_gba`, но фиксируется в `gba_eligible_groups`; (d) инвариантность к дисбалансу классов внутри группы.
* **DoD:** пересчёт `RESULTS.md` для всех пяти арм в новых метриках; ожидаем, что все дельты схлопнутся в шум — это и есть подтверждение M31.

### F4. Новый режим fitness и селектора

* **Где:** `prime/config.py`, `prime/fitness/objective.py`, `prime/controller.py::_selection_key`.
* **Как:**
  1. `fitness.group_acc: raw | balanced_global | balanced_within` (новый дефолт `balanced_within`). `_group_accs_for_lex` при `balanced_within` берёт `cluster_gba_shrunk`.
  2. Режимы `min_group_lex` / `soft_min_lex` начинают работать поверх GBA без изменения формулы: `base = softmin_τ(GBA_g) + ε · GBA_mean − len_penalty`.

* **Тест:** расширить `tests/test_soft_min_lex.py` кейсами на GBA; проверить, что `ε` действительно только тай-брейк (изменение `GBA_mean` на 0.05 не перебивает падение softmin на 0.02).

### F6. Неопределённость без ансамбля (self-consistency)

* **Где:** `prime/workers/scorer.py`, `prime/acquisition/scoring.py`, `controller.py`.
* **Как:** двухстадийная acquisition, чтобы не платить 3× за весь пул.
  1. Стадия 1: один проход `T=0` по подвыборке пула (`al_candidate_pool_size` → `pool_score_subsample`, дефолт 1200) ⇒ `err` и групповые квоты. Ранжирование как сейчас (`group_aware`).
  2. Стадия 2: берём шорт-лист `oversample_factor × batch_size` (3 × 24 = 72), гоняем `k = 3` сэмплов при `T = 0.7` ⇒ `uncertainty = 1 − max_vote_share ∈ {0, 1/3}`; внутри группы сортируем по `(err, uncertainty)`.
  3. D_anchor: те же 3 сэмпла на кандидатов якоря (100 примеров × 3) ⇒ «уверенно решён» = `err == 0 и uncertainty == 0`.
* **Цена:** (72 + 100) × 3 × n_cycles ≈ 1550 вызовов на прогон — 2–3% бюджета.
* **Тест:** `tests/test_uncertainty.py` — при трёх одинаковых голосах `uncertainty = 0`; при 2/1 = 1/3; при наличии `INVALID` пример исключается из шорт-листа.
* **DoD:** в `batch_diagnostics.json` появляется распределение `uncertainty`, и оно не константа (иначе фильтр опять пустой — прямая проверка на D5).

### F7. Контракт промпта (Prompt Contract) и валидатор

* **Где:** новый `prime/evolution/prompt_contract.py`, вызов в `openevolve_adapter` **до** скоринга и в гарнессе бейзлайнов.
* **Как:** кандидат обязан: (a) содержать ровно один плейсхолдер `{text}`; (b) содержать инструкцию формата ответа (regex на `\b0\b.*\b1\b` в блоке формата); (c) быть форматируемым (`prompt.format(text=...)` без исключения — это ровно кейс D4 со скобкой); (d) быть ≤ `prompt_len_limit`. Нарушение ⇒ одна попытка авторемонта мутатором, затем `fitness = -1e9`, `reject_reason = "contract"`.
* **Тест:** `tests/test_prompt_contract.py` — промпт с несбалансированной скобкой отвергается **до** траты вызовов.
* **DoD:** на кейсе D4 расходуется 0 API-вызовов вместо 2160.

### F8. Dev-гейт вместо ротации D_select

* **Где:** `prime/config.py` (`data_roles.d_dev_size`, `selection.dev_gate_*`), `prime/controller.py` (конец цикла), `prime/experiment/anchor_gate.py` (переиспользуем механику).
* **Как:** после выбора наследника цикла — оценить его и текущего чемпиона на фиксированном `D_dev` (не пересекается ни с D_select, ни с D_anchor, ни с test). Промоутить наследника, только если `R_soft_min_gba(D_dev)` не падает более чем на `dev_gate_delta = 0.01` относительно чемпиона. Иначе — оставить чемпиона и записать `dev_gate: rejected` в `stage_trace`.
* **Зачем:** M30 (фиксированный D_select ⇒ переобучение) против M28 (ротация ⇒ шум 12 п.п.). Dev-гейт снимает переобучение, не добавляя шума в сам поиск.
* **Тест:** `tests/test_dev_gate.py` на синтетике: наследник, который лучше на D_select и хуже на D_dev, не промоутится.
* **DoD:** в `summary.json` появляется `generalization_gap` = `fitness(D_select) − fitness(D_dev)` по циклам.

### F11. Гарнесс для чужих методов

* **Где:** новый пакет `baselines/` рядом с `prime/`.
* **Как:** единый интерфейс, чтобы ни один метод не мог «сжульничать» другим скорером или парсером:

```python
# baselines/api.py
@dataclass
class Task:
    train: LabeledSet        # S: labeled source
    dev: LabeledSet          # D_dev, для селекции внутри метода
    unlabeled: UnlabeledSet  # U: target-группы без меток
    label_budget: int        # сколько меток метод вправе запросить (0 для не-AL)
    scorer: Scorer           # ЕДИНЫЙ, F5
    optimizer_llm: LLM       # ЕДИНЫЙ, deepseek/deepseek-v4-pro
    budget: BudgetGuard      # F10
    seed_prompt: str | None
class Optimizer(Protocol):
    def run(self, task: Task) -> OptimizerResult  # best_prompt, all_candidates, trace
```

  Каждый метод — файл `baselines/<name>.py`, без правок ядра.
* **DoD:** `baselines/test_smoke.py` — все реализованные методы проходят mock-прогон за <60 с и возвращают валидный по контракту F7 промпт.

### F12. Пересборка отчётности

## 3. Блок B — какую модель оставляем

### 3.1 Решение: `google/gemma-3-12b-it`

**За:**
* Единственный воркер с реальным динамическим диапазоном: recall 0.687 при specificity 0.805. Ансамблю и gemma-4 промпт «поднять recall» физически некуда двигать без выхода из режима «почти всегда 0».

* Он же — первый воркер текущего ансамбля, т.е. вся уже накопленная история (кэш предсказаний, `worker_predictions.npy[0]`) остаётся сопоставимой: мы можем **ретроспективно** пересчитать все пять арм E4 в новой постановке без единого нового вызова API.

* `R_global` 0.7925 против 0.8688 у ансамбля — но это артефакт базовой ставки 10.4% (ALL-ZERO даёт 0.8962). На заголовок это больше не влияет (F3).
* FPR ≈ 0.195 — высокий. Это не баг, а рабочая точка: у промпт-оптимизации есть куда двигаться в **обе** стороны, что для нашей задачи лучше, чем консервативная модель без хода.

**Роли остальных:**
* `google/gemma-4-26b-a4b-it` — **transfer-scorer**. Финальные промпты всех методов один раз прогоняются на нём (test_fixed, 1 повтор) — это раздел «переносится ли найденный промпт на другую модель». В оптимизации не участвует.
* `qwen/qwen3.7-flash` — удалить из всех конфигов. Занести в `configs/REJECTED_MODELS.md` вместе с уже отклонёнными `gpt-oss-20b` и `ministral-8b`.

## 4. Блок C — метрика и выборки

### 4.1 Определения (фиксируем до прогонов)

Для группы `g ∈ {male, female, LGBTQ, christian, muslim, other_religions, black, white}`:

```
TPR_g = P(pred = 1 | y = 1, g)      TNR_g = P(pred = 0 | y = 0, g)
GBA_g = 0.5 * (TPR_g + TNR_g)
R_worst_gba = min_g GBA_g           R_gba_mean = mean_g GBA_g
```

`none` считается отдельно (`R_gba_none`) и в worst не входит.
Требование к валидности: `n_pos(g) ≥ 10` и `n_neg(g) ≥ 10`; в дизайне §4.3 всегда ≥ 100.

**Headline для статьи:** `R_worst_gba` на `test_fixed`.
**Обязательный со-репорт (иначе результат не принимается):** `R_gba_mean`, `toxic_recall`, `specificity`, `R_global`, `invalid_rate`, `pred_pos_rate`, длина промпта, `scorer_calls`.

### 4.2 Почему именно GBA, а не «worst-group accuracy» как в WILDS

WILDS считает worst-group по 16 ячейкам (identity × label) как обычную accuracy — это эквивалентно
минимуму из `{TPR_g, TNR_g}` по всем g. Мы берём **среднее** TPR/TNR внутри группы, потому что:
* минимум по 16 ячейкам при любом реалистичном n имеет вдвое большую дисперсию, а на нашем бюджете это решающе;
* min по ячейкам почти всегда указывает на `toxic ∧ small group` и деградирует до «recall на 100 примерах»;
* GBA сохраняет главное свойство — молчание даёт ровно 0.5 и не может выиграть.

Мы всё равно **репортим** и WILDS-совместимый `min_cell_accuracy` в приложении таблицы, чтобы сравнение с литературой было возможно.

### 4.3 Выборки CivilComments (все фиксируются seed'ом и фингерпринтом)

| набор | источник (WILDS split) | дизайн | n | назначение |
|---|---|---|---|---|
| `test_fixed` | test | 8 identity × 2 класса × 100 + none 100/100 | **1800** | только финальные измерения, ни один метод его не видит |
| `D_dev` | validation | 8 × 2 × 50 + none 50/50 | **900** | dev-гейт (F8) и внутренняя селекция всех методов |
| `D_select` | train | 8 identity × 2 × 45 | **720** | целевая функция поиска в Regime-Full |
| `S_source` | train, подмножество `D_select` + none | source-группы {none, male, female, christian} × 2 × 45 | **360** | «labeled source» в Regime-Shift (§6.1) |
| `U_target` | train (disjoint) | target-группы {LGBTQ, muslim, other_religions, black, white}, метки скрыты | **4000** | unlabeled target для GPO / APE-ut / нашего AL-пула |
| `L_budget` | из `U_target` | 5 групп × 2 класса × 24 = 240 меток | — | одинаковый потолок разметки для AL-методов |
| `D_anchor` | train (disjoint) | 100, стратифицирован | 100 | anchor-гейт (`reject`, δ=0.02, α=0.05) |

Деление на source/target: source = `{none, male, female, christian}` (в E4 это группы с высокой точностью),
target = `{LGBTQ, muslim, other_religions, black, white}` (по M26 именно там провал: black 0.55, LGBTQ/muslim 0.60).
`R_worst_gba` считается по всем 8 identity-группам, поэтому в заголовке видно и сохранение source, и подъём target;
дополнительно репортим `worst-GBA` отдельно по source- и target-подмножествам.

В Regime-Shift наш метод стартует с `S_source` (360) и добирает до 240 меток из `U_target` ⇒ максимум 600 размеченных;
APE/APO/EvoPrompt/GEPA работают на 360; Random-AL — на 360 + 240 случайных. Бюджет вызовов scorer'а у всех одинаковый.

Все пулы проверены по §1.1 — узкое место `other_religions` (val 79 токсичных при потребности 50, test 240 при потребности 100) укладывается.

Пересечения: `test_fixed` из test-сплита, `D_dev` из validation, всё остальное из train ⇒ утечка невозможна по построению сплитов WILDS. Внутри train — жёсткая проверка непересечения индексов в `tests/test_balanced_cells.py`.

### 4.4 Мощность

При `n_pos = n_neg = 100` на группу: `SE(GBA_g) ≈ 0.5·√(0.25/100 + 0.25/100) ≈ 0.035`.
Для парных сравнений (один и тот же `test_fixed`, два промпта) используем McNemar и парный bootstrap по примерам —
там определяющей является доля расхождений, а не абсолютный n; на прошлых прогонах чистых расхождений было 100–200 на 800,
т.е. MDE по `R_global` ≈ 0.02. Для `R_worst_gba` планируем MDE ≈ 0.05 — это соответствует тому, что заявляют APO/GPO-работы
(они рапортуют 3–10 п.п. на target-группах).

## 6. Блок E — бейзлайны: что берём и как запускаем честно

### 6.1 Постановка, в которой сравниваем (главное решение о «честности»)

Наш научный тезис — «worst-group робастность при ограниченном бюджете разметки». Поэтому режим такой:

* дано: `S_source` (размечено, 4 «лёгкие» группы), `U_target` (4000 примеров из 5 «тяжёлых» групп, **без меток**), `D_dev` (для внутренней селекции — доступен всем), бюджет разметки `L = 240` меток из `U_target`;
* каждый метод пользуется тем, чем умеет:

| Метод | S_source | U_target (тексты) | L (право разметить) | Комментарий |
|---|:---:|:---:|:---:|---|
| Seed prompt | — | — | — | пол |
| ALL-ZERO / ALL-ONE | — | — | — | пол, ловушка на метрику |
| APE | ✓ | — | — | нативно; «direct generalization» строка из GPO-статьи |
| APO / ProTeGi | ✓ | — | — | нативно |
| EvoPrompt (GA, DE) | ✓ | — | — | нативно |
| GEPA | ✓ | — | — | нативно |
| OPRO (опц.) | ✓ | — | — | нативно |
| APE-ut | ✓ | ✓ (в мета-промпт) | — | из GPO-статьи |
| **GPO** | ✓ | ✓ (псевдо-метки K=6, T=0.83) | — | целевой конкурент |
| **PRIME (наш)** | ✓ | ✓ (пул) | ✓ 240 | AL — и есть наш механизм |
| **Random-AL контроль** | ✓ | ✓ | ✓ 240 случайных | отделяет «мы умеем выбирать» от «у нас просто есть метки» |
| **Oracle upper bound** | ✓ | ✓ полностью размечен | ∞ | строка Upper Bound из GPO-статьи |

Ключевой контроль — **Random-AL**: это APO (или EvoPrompt) с `S_source ∪ 240 случайных размеченных target-примеров`.
Если PRIME не бьёт Random-AL, значит наш вклад — не в active learning, и это надо признать прямо.

**Вторая, более простая постановка (Regime-Full, для приложения):** всем методам доступен полностью размеченный
`D_select` (720, все 8 групп). Тут PRIME теряет преимущество по данным и остаётся только объектив + эволюция.
Считаем её обязательной: она отвечает на вопрос «наш выигрыш — от метода или от доступа к меткам».

### 6.3 Жёсткие правила честности (нарушение = прогон не засчитан)

1. **Один scorer** — `Scorer` из F5. Ни один метод не имеет своего инференса.
2. **Один парсер и одна политика отказов** — F1. `INVALID` считается ошибкой у всех одинаково.
3. **Один контракт промпта** — F7. Иначе метод может выиграть за счёт формата вывода, а не содержания.
4. **Один optimizer LLM** — `deepseek/deepseek-v4-pro`. Температуры — нативные для каждого метода.
5. **Один кап бюджета** — `scorer_calls ≤ 60 000`, `optimizer_calls ≤ 400`. Обе цифры в отчёте.
   Методы, которые нативно тратят меньше, репортятся дважды: «native» и «budget-matched».
6. **Один тест** — `test_fixed`, фингерпринт в каждом артефакте; ни один метод его не видит в процессе.
7. **Одна процедура отбора финального промпта** — «Top-1 по `R_soft_min_gba` на `D_dev`». Дополнительно репортим
   «Ensemble по K промптам» для APE/GPO, как в их статье (это их нативный протокол), но headline — Top-1.
8. **Три сида** (42, 43, 44) на каждый метод; сид меняет и данные (сэмплинг S/U/D_select), и LLM-сэмплирование.
9. **Все финальные замеры — в один день/одну сессию** (M29), с 3 повторами и одновременным ре-скорингом seed-промпта.

### 6.4 Gate достоверности реимплементации (обязательный)

Прежде чем верить нашим цифрам по чужим методам, мы обязаны показать, что реализовали их правильно.
Проверка на **родной для GPO задаче**: sentiment, Yelp (source) → Flipkart (target), 36-shot, K=6, T=0.83.

**Критерий:** наш GPO должен на target-группе превзойти наш APE (в статье это устойчивый эффект),
а APO должен превзойти APE на source. Если не воспроизводится — чиним реимплементацию, а не запускаем E5.
Стоимость: ~4 прогона × ~10k вызовов на дешёвом scorer'е.

### 7.2 Вторая площадка: Amazon-WILDS

Запускаем сокращённый набор {Seed, APE, APO, GPO, PRIME-main, Random-AL} × 3 сида на том же скелете.
Цель — не победа (M18/M20 говорят, что там ловить нечего), а **проверка, что новая измериловка не рождает ложных выигрышей**
на площадке, где мы уже доказали отсутствие сигнала. Если на Amazon все методы неразличимы — это подтверждение
корректности стенда; если кто-то «выигрывает» — стенд снова врёт.

Метрика там — та же логика внутригруппового баланса, но группы = категории/пользователи, классы = 1–5 ⇒
`GBA_g` заменяется на macro-per-class accuracy внутри группы. Реализация — отдельная задача, не блокирует CivilComments.

### 7.3 Статистика и предрегистрация

До первого прогона фиксируем в `experiments/E5_civilcomments/PREREGISTRATION.md`:
* headline = `R_worst_gba` на `test_fixed`, Top-1 по `D_dev`;
* основной тест — парный **bootstrap по примерам** (10 000 итераций, стратифицированный по ячейкам) для CI95 на разности `R_worst_gba` между методом и seed-промптом; вторичный — McNemar на `R_global`;
* агрегация по сидам — среднее ± SD, плюс «сколько из 3 сидов дали положительную дельту»;
* поправка на множественность — Holm по числу методов для основного сравнения;
* **критерий успеха нашего метода:** `ΔR_worst_gba ≥ +0.05` против seed-промпта, CI95 не пересекает 0, и `≥ +0.02` против лучшего из {APO, GPO, Random-AL};
* **критерий честного провала:** если PRIME ≤ Random-AL, пишем это в OBSERVATIONS как M-запись и меняем гипотезу, а не метрику.

Всё, что не предрегистрировано, идёт в раздел «exploratory» и не может быть заголовком.

| Шаг | Содержание | Gate |
|---|---|---|
| S1 | F1, F2, F7 (fail-closed, guard, контракт) + тесты | кейс D4 отвергается за 0 вызовов |

prompt-only оптимизация группы не чинит» — и это тоже публикуемый результат, но он требует другой обвязки
(тогда добавляем ещё одну модель и ещё одну задачу, чтобы утверждение было не про один чекпойнт).

## 8. Риски и как их закрываем

| Риск | Проявление | Митигация |
|---|---|---|
| Модель нечувствительна к промпту | все методы дают Δ ≈ 0 | S5 pre-flight; запасные scorer'ы |
| Новая метрика тоже окажется вырожденной | worst-GBA не двигается ни у кого | S6 проверяет полы (ALL-ZERO = 0.5) и разброс по 6 промптам; в отчёт всегда идут TPR/TNR по группам |
| Реимплементация чужого метода слабее оригинала | «мы всех побили» | S7 gate на родной задаче GPO; публикуем код бейзлайнов; репортим native + budget-matched |
| Наш выигрыш — только от лишних меток | PRIME > APO, но = Random-AL | Random-AL как обязательная строка; Regime-Full как вторая постановка |
| Дрейф API между днями (M29) | ложные дельты | все финальные замеры одной сессией + одновременный ре-скоринг seed |
| Переобучение на D_dev (мы им и селектим, и гейтим) | оптимистичная селекция | `test_fixed` не участвует нигде; в отчёте показываем `dev → test` разрыв для каждого метода |
| Бюджет/время | 45 ч машинного времени | ночные батчи, кэш предсказаний по (prompt_hash, example_id), опциональный cascade-скрининг (`scripts/exp_cascade_screen.py`) |
