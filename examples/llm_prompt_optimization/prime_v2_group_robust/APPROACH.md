# GRAPE: Group-Robust Prompt Evolution
### Полное описание подхода с нуля — основания, механика, аргументы, применимость

Рабочее имя метода: **GRAPE** (Group-Robust Adaptive Prompt Evolution).
Кодовая база: `prime_v2_group_robust/` (PRIME v2). Этот документ — самодостаточное
описание подхода: его можно читать без истории v1.

---

## 1. Задача и главная идея в одном абзаце

Есть замороженная LLM-система разметки (одна модель или ансамбль за API) и целевой
домен, в котором данные порождаются **разнородными источниками** — пользователями,
авторами, госпиталями, юрисдикциями, временными периодами. Качество разметки на
«среднем» источнике приемлемое, но на хвосте распределения источников — проваливается,
и именно хвост определяет пригодность системы к деплою (worst-group метрики).
Веса менять нельзя или невыгодно. **GRAPE адаптирует единственный артефакт — текстовый
промпт — так, чтобы явно оптимизировался хвост распределения групп, а не среднее.**
Для этого: (i) скрытые группы выводятся из поведения источников без разметки групп,
(ii) эволюционный поиск промпта ведётся по робастному CVaR-объективу поверх этих групп,
(iii) батчи для обучения промпта собираются активно из худших групп,
(iv) архив эволюции хранит промпты-«специалисты» по разным группам и сливает их
комплементарные уроки, (v) итоговый промпт содержит правила, обусловленные типом
источника (по умолчанию — неявно, через условные правила в одном промпте;
опционально — через явную сборку блока под группу, §4.6), — и потому переносится
на **новые, не виденные** источники того же типа.

## 2. На чём основан подход (четыре опоры)

### Опора 1. Latent group discovery — из weight-space в prompt-space
В классической робастности известно: когда групповые метки на тесте недоступны,
группы можно **вывести**: GEORGE (Sohoni et al., NeurIPS'20) кластеризует признаки
модели и запускает GroupDRO по найденным субклассам; EIIL (Creager et al., ICML'21)
выводит «окружения», максимизируя инвариантностный штраф; JTT (Liu et al., ICML'21)
использует множество ошибок ERM-модели как прокси меньшинств. Все они делают это,
чтобы затем **обучать веса**. GRAPE переносит этот приём в мир, где весов нет:
группы = кластеры **поведенческих профилей источников**, а робастная оптимизация
идёт в дискретном пространстве промптов.

### Опора 2. DRO/CVaR-объектив + эволюционный поиск = естественная пара
GroupDRO (Sagawa et al., ICLR'20) и CVaR-DRO (Levy et al., NeurIPS'20) оптимизируют
худшие группы, но в градиентном мире это капризно: min-max нестабилен, требует
регуляризации и малых шагов. Ключевое наблюдение GRAPE: **эволюционному поиску
всё равно, что объектив негладкий, шумный и min-max** — популяционный отбор по
скалярному fitness не требует градиентов вообще. Дискретный промпт нельзя учить
градиентами, зато робастные objectives ему «бесплатны». Мы превращаем главный
недостаток prompt-space (недифференцируемость) в преимущество.

### Опора 3. Query-by-Committee + активный отбор
Несогласие комитета моделей — классический сигнал информативности (Seung et al., 1992).
В GRAPE ансамбль гетерогенных LLM даёт ordinal-aware disagreement d_i **без меток**;
вместе с ошибкой majority vote это даёт ранжирование примеров (лексикографически,
без магических весов). Батч собирается двухуровнево: между группами — пропорционально
их текущей слабости, внутри группы — по рангу информативности с diversity-отбором
(идея Cluster-Margin/BADGE: uncertainty × разнообразие). Anchor-часть батча
(replay против забывания) — идея из continual learning, отсутствующая в классическом AL.

### Опора 4. Quality-Diversity: архив по профилям групповой точности
MAP-Elites/QD-поиск хранит разнообразие по «поведенческим дескрипторам». GRAPE
определяет дескриптор кандидата как **профиль per-group accuracy**: архив обязан
удерживать промпты, сильные на разных группах, даже если их средний fitness ниже.
GEPA (ICLR'26) показала, что Pareto-фронт кандидатов критичен против локальных
оптимумов; GRAPE специализирует эту идею: ось разнообразия = робастность по группам.
Между AL-циклами переносится **пул** элитов по группам (не одна точка), а
консолидация LLM-ом получает явное задание «слей комплементарных специалистов,
сохранив правила, за которые каждый отвечает» — merge комплементарных уроков
в духе GEPA, но с групповой адресацией.

## 3. Формальная постановка

Дано: пул неразмеченных входов U = {x_i} из целевого домена, каждый с идентификатором
источника s(x_i) (пользователь/госпиталь/период — метаданные, не метка задачи);
малый размеченный поднабор L ⊂ U (в пределе |L| → 0 — label-lean режим);
замороженный предиктор ŷ(x; P) = агрегация {f_m(x; P)} по M воркерам с общим промптом P.

Выводим отображение g: s → {1..K} (источник → латентная группа) из поведенческих
профилей источников. Цель:

  P* ∈ argmax_P  CVaR_α[ Acc_k(P) ]_{k=1..K},

где Acc_k — точность на группе k, CVaR_α — среднее по худшей α-доле групп
(α ≈ 1/3; не строгий минимум — контроль шума). Ограничения: P — структурированный
текст; бюджет вызовов API ≤ B; на деплое доступен только x. В базовом режиме
группа на деплое не нужна (правила обусловлены наблюдаемыми признаками текста,
LLM «маршрутизирует» сам); в режиме условной сборки (§4.6) группа вычисляется
на тесте label-free проекцией и определяет подставляемый блок промпта.

## 4. Как это работает: шесть компонентов

### 4.1 Вывод групп (Behavioral Group Inference)
1. Для каждого источника в train: профиль = [средний эмбеддинг его текстов ‖
   поведенческие статистики] (длина, пунктуационная плотность, доля капса,
   для рейтинговых задач — средняя оценка и дисперсия как калибровка шкалы).
2. Стандартизация признаков (StandardScaler) + балансировка блоков: эмбеддинг
   сжимается PCA до ~32–64 компонент, чтобы 384-мерный текстовый блок не подавил
   поведенческие скаляры. k-means, K ∈ {6..10}; выбор K — по silhouette + стабильности
   по сидам (не «магическое число»).
3. **Двухвидовое назначение (анти-утечка):** центроиды хранятся в двух проекциях —
   полной (для train) и **label-free** (только текст+длина, без rating-статистик).
   Новые источники (val/test/деплой) назначаются к ближайшему центроиду в label-free
   проекции. Так groups на тесте не зависят от gold-меток даже косвенно; согласие
   двух проекций на train — диагностика качества кластеров.
4. Прокси-валидация (встроена в цикл, не post-hoc): корреляция CVaR_cluster ↔
   официальная worst-group метрика на val. Если корреляция слабая — кластеры чинить
   до дорогих прогонов (другое K, другие признаки), это дешёвый ранний детектор.

### 4.2 Активный отбор (Group-Weighted Acquisition)
Каждому примеру Seen-пула: err_i ∈ {0,1} (если есть метка), d_i ∈ [0,1]
(ordinal disagreement воркеров, без меток). Батч B (80):
- **Между группами:** квоты Hard-слота ∝ (1 − Acc_k), т.е. слабые группы получают
  больше мест (не бинарное «по одному примеру на кластер», а взвешивание слабостью).
- **Внутри группы:** ранжирование лексикографически (err, d) → top-k с oversample ×3 →
  k-means-diversity по текстам **внутри** топа.
- **Anchor (30%):** низ ранжирования, стратифицированный по классам × группам —
  replay против забывания уже решённых типов.
- **Expansion:** когда слабые группы исчерпаны в Seen — подкачка из Unseen по d_i
  (один дешёвый прогон) с покрытием групп.
Label-lean: та же механика при err_i = None — ранжирование по d_i (чистый QbC).

### 4.3 Эволюция с робастным fitness
Внутренний цикл — OpenEvolve (LLM-мутатор + архив):
  fitness(P) = w_c·CVaR_группы(P) + w_g·Acc_global(P) + w_k·κ(P) − penalty_len(P).
Мутатор получает **групповой отчёт об ошибках**: per-group точность, топ-confusion
на худших группах, примеры ошибок с пометкой типа источника, и явное право писать
**type-conditional правила** («если отзыв краткий и гиперболизированный — проверь
сарказм, прежде чем ставить максимум»).

**Структурный промпт — не форматирование, а механизм.** В v1 XML-структура была
оболочкой без измеримого выигрыша; в GRAPE у каждого блока появляется рабочая роль:
- `<BaseGuidelines>` — групп-инвариантное ядро. Медленная шкала времени: правится
  редко, на данных всех групп; единственная цель консолидации; защищено от
  группоспецифичного churn.
- `<DynamicRules>` — носитель type-conditional правил. Быстрая шкала: мутируется
  каждый цикл по групповым отчётам. В режиме условной сборки (§4.6) — единица
  подстановки под группу.
- `<FewShotExamples>` — стилевые примеры-двойники, нацеленные на худшие группы
  (синтетический генератор получает стиль группы как спецификацию).
- Мутации **scoped**: одна мутация правит один блок по отчёту ошибок конкретной
  группы — контролируемый credit assignment вместо переписывания всего текста
  (снижает деструктивную интерференцию «починили группу 3 — сломали группу 5»).
Абляция «структура on/off» теперь проверяет содержательную гипотезу (структура =
две шкалы времени + scoped-мутации + условная сборка), а не пользу XML-тегов.

### 4.4 QD-архив и перенос между циклами
Дескриптор кандидата в архиве = вектор per-group accuracy (+ длина промпта).
Между AL-циклами переносится пул: элита по каждой группе + глобальный лучший
(3–5 промптов), консолидированный промпт добавляется **кандидатом**, не наследником.
Консолидация видит, какой специалист какую группу закрывает, и сшивает правила
адресно. Одноточечного бутылочного горлышка (дефект v1) нет.

### 4.5 Отбор и сертификация
Между циклами промпт выбирается лексикографически: сначала CVaR_val по группам,
при близости — глобальная точность. Гейт: не принимать промпт, ухудшивший любую
нижнюю группу сверх допуска. Финальный отчёт: официальная worst-group метрика
бенчмарка + CVaR по группам + bootstrap-CI по источникам + ID-vs-OOD gap
(промпт на held-out источниках train-распределения vs test-источниках) — gap
меньше ⇒ адаптация не оверфитится на распределение оптимизации.

### 4.6 Спектр маршрутизации: сколько явного роутинга нужно?

После вывода групп есть три способа донести групповые правила до инференса —
это спектр, и он же отдельная исследовательская ось статьи:

- **A. Неявная маршрутизация (дефолт).** Один промпт, условные правила по
  наблюдаемым признакам текста; LLM роутит сам. Кластер на тесте не нужен.
- **B. Условная сборка (главный претендент).** Общий `<BaseGuidelines>` +
  подставляемый блок `<DynamicRules cluster=k>` (и few-shot примеры группы k).
  На тесте источник назначается в кластер label-free проекцией (§4.1.3),
  меняется только блок.
- **C. Mixture-of-prompts (абляция).** K независимых промптов-специалистов +
  роутер. Крайняя точка спектра.

**За явный роутинг (B/C):** (i) снимается недоказанная ставка на неявный роутинг
LLM — при K групп правила в одном промпте растут линейно, интерферируют и
разбавляются (lost-in-the-middle); в B в контексте только релевантный блок —
короче и дешевле; (ii) чистый credit assignment: блок k мутируется по ошибкам
только группы k; (iii) естественная стыковка с QD-архивом — элита группы k
становится кандидатом в блок k, а консолидация нужна только базе (проблема
бутылочного горлышка почти исчезает).

**Против (ключевой риск):** ошибки роутера **анти-коррелированы с целью** —
nearest-centroid назначение хуже всего работает на атипичных источниках, а именно
они образуют оптимизируемый хвост; worst-group метрика системы = min по композиции
(роутер ∘ специалист), и специалист вне своей группы может быть хуже генералиста.
Плюс: кластеры построены на *профилях* (агрегатах), а в стриминге первый текст
нового источника роутится по одному примеру — шумно; фрагментация данных
(K специалистов × 1/K примеров → оверфит каждого); артефакт деплоя перестаёт
быть одной строкой (нужны эмбеддер + центроиды).

**Решение GRAPE:** дефолт — A; B — первоклассный вариант со страховками:
1. **Abstention-fallback:** расстояние до ближайшего центроида > порога
   (атипичный источник) → генералистский промпт A. Хвост защищён от роутера.
2. **Общая база:** цена misrouting мала, т.к. отличается только блок.
3. **Порог данных:** группе с < N размеченных примеров отдельный блок не
   выделяется — её правила остаются в общем `<DynamicRules>`.
4. **Честная оценка:** все end-to-end метрики — с предсказанным роутингом,
   никогда с oracle-кластерами; качество роутера логируется отдельно
   (agreement label-free vs full проекции на held-out train-источниках).
Эксперимент-лестница A vs B vs C («сколько явной маршрутизации нужно
робастности в prompt-space») — самостоятельный вклад; при этом новизна метода
остаётся в робастном объективе + label-free группах, а не в роутинге как таковом
(роутинг per se — территория mixture-of-prompts/PfR).

## 5. Почему это должно выстрелить

**Механический аргумент.** Ошибки под group-shift систематичны по типам источников
(сарказм кратких рецензентов, шкальная строгость, диалект), а промпт — это явная
текстовая политика. Правило, сформулированное про *тип* («краткий + гипербола →
проверь сарказм»), обобщается на новых носителей того же типа автоматически —
в отличие от любой адаптации, привязанной к id источников. Мы оптимизируем ровно
тот носитель (текст правил), который по своей природе обобщается по типам.

**Структурный аргумент.** Эволюция + DRO — редкая пара, где недостатки взаимно
гасятся: DRO негладок — эволюции всё равно; промпт недифференцируем — DRO не нужен
градиент; QD-архив по групповым профилям прямо противодействует известному режиму
отказа generic-оптимизаторов (схлопывание в «средне-хороший» промпт). Наши же
данные v1 показали этот режим: EvoPrompt и групп-агностичный PRIME упираются в
одинаковый worst-group плато при разном среднем — хвост именно там, где generic
методы не работают, т.е. headroom существует.

**Аргумент ниши.** Дискретные оптимизаторы промптов (APO/OPRO/EvoPrompt/GEPA/SPO)
не проектировались и не проверялись под сдвиг; робастные методы (GroupDRO/JTT/GEORGE/
PfR) требуют весов или обучаемой головы. Пересечение пусто — GRAPE его занимает,
при этом опираясь на зрелые опоры с обеих сторон (не «новая экзотика», а перенос
проверенных принципов в новое пространство).

**Аргумент стоимости.** Вся адаптация — вызовы API + один финальный промпт.
Ни GPU, ни весов, ни инфраструктуры деплоя: артефакт копируется строкой в любой
стек, где уже есть промпт.

**Встроенная страховка.** Если group-aware механика даст малый прирост — тот же
экспериментальный каркас публикуется как первое систематическое исследование
prompt-оптимизаторов под сдвигом (само по себе цитируемый результат), с честным
анализом, почему хвост труден для prompt-space адаптации.

## 6. Общая применимость: рецепт за пределами WILDS

GRAPE применим, когда выполняются четыре условия:
1. **Есть источники**, порождающие коррелированные входы (юзер, автор, госпиталь,
   филиал, юрисдикция, канал, временное окно) — id источника доступен при адаптации,
   на деплое не нужен.
2. **Есть неразмеченный пул** целевого домена и малый размеченный поднабор
   (или возможность разметить десятки–сотни примеров; в пределе — label-lean по d_i).
3. **Задача решается инструкцией**: замороженная LLM в принципе способна на задачу,
   вопрос в спецификации (классификация, извлечение, оценка по рубрике, модерация).
4. **Метрика деплоя — хвост**, не среднее.

Модуль групп — подключаемый, три режима:
- **oracle** (группы известны: identity-атрибуты CivilComments, id госпиталя,
  язык тикета) — кластеризация не нужна, GRAPE работает по данным группам;
- **inferred** (группы скрыты: стили рецензентов Amazon) — поведенческая
  кластеризация из §4.1;
- **hybrid** (грубые группы известны, тонкие — нет): кластеризация внутри oracle-групп.

Примеры инстанцирования:
| Домен | Источник | Сдвиг | Группы |
|---|---|---|---|
| Amazon-WILDS (старт) | рецензент | новые пользователи | inferred стилевые кластеры |
| CivilComments-WILDS | комментарий/identity | группы идентичности | oracle |
| Клинические заметки | госпиталь/врач | новые госпитали | oracle id + inferred стиль записей |
| Тикеты поддержки | продукт/регион/язык | новый регион или релиз | hybrid |
| Модерация UGC | сообщество/платформа | новые сообщества, дрейф сленга | inferred + временные окна |
| Юр. документы | юрисдикция | новая юрисдикция | oracle |

Времянно́й дрейф — частный случай: «источник» = временное окно, worst-group =
худшие окна; GRAPE превращается в промпт-адаптацию к дрейфу без переобучения.

**Когда GRAPE не сработает (честные границы):**
- концепт-сдвиг за пределами выразимости инструкции (нужны новые *знания*, не
  правила — территория RAG/FT);
- группы не проявляются в наблюдаемом поведении источников (кластеры не выводимы);
- модель фундаментально не способна на задачу (промпт не добавит компетенции);
- крошечный пул (<сотен примеров) — нечего активно отбирать.

## 7. Соответствие кодовой базе и дельты

Уже реализовано в `prime/`: официальные WILDS-сплиты; профили источников и k-means
с сериализацией и nearest-centroid назначением; CVaR-метрики и конфигурируемый
fitness (mode: cvar|global|v1_weighted, веса в YAML); лексикографический scoring
c policy-параметром; top-k + diversity + базовые квоты в batch_builder;
per-cluster error artifacts для мутатора; pool_carryover c опцией cluster_pareto;
selection с весом CVaR; bootstrap-статистика; E1-пилот (cvar vs global) как go/no-go.

Дельты до полного GRAPE (в порядке приоритета):
1. **Label-free проекция назначения** (§4.1.3): assign по тексту+длине без
   rating-статистик; хранить обе проекции центроидов (`clustering.py`).
2. **StandardScaler + PCA-балансировка** блоков признаков (`profiles.py`).
3. **Настоящий group-weighted acquisition**: квоты ∝ (1−Acc_k) вместо сортировки
   `(err, d, −cluster_id)` и «≥1 на кластер» (`scoring.py`, `batch_builder.py`);
   политика `group_aware` должна принимать текущие per-group accuracy.
4. **QD-дескрипторы**: feature_dimensions архива = профиль per-group accuracy
   (сейчас частично: `["prompt_length", "CVaR_cluster"]`), `cluster_pareto: true`
   по умолчанию после проверки.
5. **Прокси-валидация** CVaR_cluster ↔ R_worst на val как обязательный лог цикла.
6. Убрать бинарный префильтр hard-кандидатов (`err>0 or d>0`) — чистое ранжирование.
7. Отключаемый и **громкий** synthetic-fallback кластеров (сейчас случайные
   эмбеддинги могут тихо подменить реальные в smoke-режиме).
8. **Scoped-мутации по блокам** (§4.3): мутатор получает целевой блок + групповой
   отчёт; консолидация применяется только к `<BaseGuidelines>`.
9. **Условная сборка (режим B, §4.6)**: `prompt_mode: implicit|assembled|mixture`
   в конфиге; сборщик промпта по кластеру, abstention-порог по расстоянию до
   центроида, лог качества роутера. Реализуется после E1 и дельт 1–3 —
   отдельным экспериментом «routing spectrum» (A vs B vs C).

Порядок проверки гипотез: E1 (cvar vs global) → дельты 1–3 → E2-лестница →
routing spectrum (дельты 8–9).
