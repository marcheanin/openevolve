# GRAPE — целевой сценарий обучения (per-group Парето)

Статус: **целевая механика** по `SPEC.md` §4.6 / §4.3 (не снимок текущего кода).  
Схема: [`grape_target_pareto_loop.png`](grape_target_pareto_loop.png).

В коде сейчас дефолт проще: `cluster_pareto: false`, carryover = top-k по скалярному fitness, следующий цикл часто стартует с одного промпта (лучший по val). Ниже — как должно работать в полном GRAPE; это же проверяется абляцией E2.6 и E-абляцией carryover.

---

## 0. Что оптимизируется

Веса LLM не меняются. Эволюционирует только текстовый промпт при бюджете API-вызовов.

Цель: качество на худшем хвосте латентных типов источников (CVaR по типам), с переносом на новых авторов. Официальный арбитр на Amazon-WILDS — `R_worst` (10-й перцентиль точности по `user_id`).

Инварианты:

1. **Тип, не носитель** — правила про поведение класса авторов, не про конкретных user_id.
2. **Хвост, не среднее** — отбор кандидатов и родителей мутации не усредняет прогресс на слабых типах.
3. **Бюджет = вызовы** — дорогие оценки только там, где решение информативно.

Ключ к инварианту 2 между циклами и внутри цикла — **per-group Парето-фронт**, а не один «лучший по среднему / CVaR» промпт.

## 1. Один раз в начале рана (потом заморожено)

### 1.1 Официальные сплиты

`train` / `validation` / `test` (WILDS). Пользователи между сплитами не пересекаются.  
`test` до конца рана не используется для выбора промпта.

### 1.2 Разрез train по источникам

По `user_id`, примерно 70/30:

| Множество | Роль |
|---|---|
| **fit_sources** | кластеры (типы), acquisition pool, минибатчи мутатора |
| **heldout_sources** | внутренний судья кандидатов (репетиция OOD) |

Разрез фиксирован на весь ран.

### 1.3 Типы τ

На пользователях fit: средний эмбеддинг отзывов (PCA) + стилевые статистики → k-means.  
Рейтинг в геометрию не входит. Пользователи с числом отзывов &lt; `min_reviews_for_fit` не двигают центроиды, но потом назначаются к ближайшему типу.

Теми же центроидами назначают тип на heldout, val, test.  
Геометрия типов дальше не переучивается.

### 1.4 Фиксированные наборы из heldout

| Набор | Размер (полный / capped E1) | Обновление | Роль |
|---|---|---|---|
| **D_select** | ~400 / 200 | нет | fitness, вектор Acc по типам, Парето-фронт, carryover |
| **D_anchor** | ~100 / 50 | нет | регрессионный гейт при приёмке |

Дизъюнктны. Все сравнения кандидатов и срезы фронта — на **одном и том же** `D_select`, иначе carryover между циклами несравним.

### 1.5 Acquisition pool (только fit)

Большой склад индексов отзывов fit:

- `pool_indices` — кап кандидатов;
- `seen` — уже открытые (с них режут `D_mut`);
- `unseen` — резерв для expansion.

Это не четвёртый «ролевой» набор статьи, а резервуар под `D_mut`.  
Старт: небольшой случайный `seen`; дальше `seen` может расти.

### 1.6 Стартовый промпт и пустой фронт

Цикл 1: входной промпт-пул = `{initial}`.  
Фронт `F` пуст и наполняется по мере первых полных оценок на `D_select`.

## 2. AL-цикл t (целевой)

### Шаг 1 — входной промпт-пул = срез фронта

На вход цикла подаётся не один промпт, а **пул 3–5** из среза Парето-фронта прошлого цикла `F_{t-1}`:

- элита на каждый тип (промпт, лучший или в CI лучшего на этом типе);
- плюс глобальный лучший по скалярному критерию (CVaR / lex), если его ещё нет в срезе.

Это устраняет bottleneck v1 («архив сбросили → выжил один промпт»).

### Шаг 2 — собрать D_mut (~35) из seen

Адверсариальный корм мутатору (пересобирается каждый цикл):

- квоты по типам ∝ `(1 − Acc_τ)`, где **Acc_τ берётся с D_select** (несмещённая слабость групп);
- внутри типа — ранг `(err, d)` и diversity по тексту.

`D_mut` не участвует в финальном fitness и не формирует фронт.

### Шаг 3 — внутренняя эволюция с родителями с фронта

OpenEvolve мутирует промпты.  
**Родитель следующей мутации** сэмплируется с **текущего** фронта `F`:

- вес ∝ числу типов, на которых промпт лидирует (или в CI лидера);
- специалист по слабому типу размножается даже при низком среднем fitness (инвариант «хвост, не среднее»).

Мутатор получает: ошибки с `D_mut`, дескрипторы типов, changelog правил предков; пишет style-conditional правила.

### Шаг 4 — per-group Парето-фронт F (ядро)

Каждый выживший до полной оценки кандидат получает на `D_select` вектор

\[
\big(\widetilde{\mathrm{Acc}}_1,\ldots,\widetilde{\mathrm{Acc}}_K\big)
\]

со Beta-сглаживанием по типам.

**Приёмка во фронт:** кандидат остаётся в `F`, если он лучший (или в доверительном интервале лучшего) **хотя бы на одном** типе τ.

Скалярный

\[
\mathrm{fitness} = \mathrm{CVaR}_{shrunk} + \varepsilon\cdot\mathrm{Acc}_{global} - \mathrm{penalty}_{len}
\]

нужен для логов, тай-брейков и удобного ранжирования, но **не заменяет** фронт как структуру селекции и carryover.

### Шаг 5 — каскад бюджета и обновление F

1. Оценка на `D_mut` — локальный отсев («не хуже родителя?»).
2. Шард `D_select` — грубая проверка зоны фронта (с учётом CI).
3. Полный `D_select` + гейт `D_anchor` — запись в архив / обновление фронта `F`.

Составы `D_select` и `D_anchor` не меняются; меняются предсказания и членство во фронте (кэш предсказаний делает повторы дешёвыми).

### Шаг 6 — carryover = срез F на цикл t+1

Между циклами переносится **срез фронта** (3–5 промптов), а не один чемпион.  
Все их метрики уже согласованы через общий `D_select`.

Опционально: консолидация `BaseGuidelines` из комплементарных специалистов → отдельный кандидат (не единственный наследник), снова через каскад и CI / `D_anchor` гейт.

### Шаг 7 — официальный WILDS validation

Раз в цикл: метрики на val, в том числе `R_worst`.  
Выбирается сертифицируемый `P*` для финального теста (межцикловой арбитр).  
Логируется corr(`CVaR_cluster`, `R_worst`) — здоровье суррогатных типов.

Val **не** подменяет фронт на `D_select`: фронт ведёт эволюцию; val защищает от оверфита внутреннего суррогата.

### Шаг 8 — expansion acquisition pool

При необходимости: часть `unseen` → `seen` (по disagreement и покрытию слабых типов).  
Растёт только резервуар под будущие `D_mut`.  
`D_select` / `D_anchor` / разрез fit–heldout / центроиды **не** трогаются.

Затем `t ← t+1`, вход = срез `F_t`.

## 3. Конец рана

Один прогон `P*` на официальном **test** → `R_worst`, CVaR, bootstrap-CI, ID–OOD gap.  
Test во время циклов для выбора не использовался.

---

## 4. Что меняется и что нет

| Объект | Меняется в циклах? | Комментарий |
|---|---|---|
| fit / heldout пользователи | нет | разрез один раз |
| типы τ, центроиды | нет | fit один раз |
| **D_select**, **D_anchor** | нет (состав) | фиксированы на ран |
| Acquisition pool `seen`/`unseen` | да | expansion |
| **D_mut** | да | заново каждый цикл |
| **Фронт F** | да | ядро селекции |
| Промпт-пул на входе цикла | да | срез F |
| `P*` (лучший по val) | да | межцикловой арбитр |
| WILDS test | один раз в конце | сертификация |

## 5. Чем это отличается от legacy / текущего кода

| | Legacy / сейчас часто | Целевой Парето-сценарий |
|---|---|---|
| Вход следующего цикла | один промпт (best@val или best fitness) | срез фронта 3–5 |
| Родитель мутации | из архива OpenEvolve / по fitness | сэмпл с F, вес ∝ лидерству по типам |
| Carryover | top-k по скаляру (`cluster_pareto: false`) | срез per-group фронта |
| CI при приёмке во фронт | нет | да |
| Модуль | заготовка `_cluster_pareto_select` | `pareto_front.py` (Фаза 3 SPEC) |

Абляции (после реализации): collapse-to-one (v1) vs пул top-k vs per-group фронт; ступень E2.6 в лестнице компонентов.

---

## 6. Короткая формула сценария

```
заморозка: fit/heldout, типы τ, D_select, D_anchor
цикл:
  пул ← срез F
  D_mut ← seen (квоты с Acc на D_select)
  эволюция: родители с F
  каскад → полный D_select обновляет F
  carryover ← срез F
  val → P*
  seen ← expansion
финал: test(P*) → R_worst
```

**fit кормит и растёт; heldout судит на фиксированных наборах; фронт F ведёт эволюцию и carryover; val выбирает сертифицируемого; test говорит один раз.**
