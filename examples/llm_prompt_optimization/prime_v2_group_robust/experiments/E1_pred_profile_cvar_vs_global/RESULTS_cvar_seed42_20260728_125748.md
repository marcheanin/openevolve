## 3. The finding that matters: consolidation eats the evolution gain

Same D_select all three cycles, so these numbers are directly comparable:

| Transition | best in OE | re-measured on entry to next cycle | delta |
|------------|-----------|------------------------------------|-------|
| C1 → C2 | 0.5826 | 0.5679 | **−0.0147** |
| C2 → C3 | 0.6127 | 0.5462 | **−0.0665** |

Between those two points the prompt passes only (a) the anchor gate, which accepted it
unchanged, and (b) `11b_base_consolidation`, which rewrote `<BaseGuidelines>`. Evolution
earned +0.133 over the run; consolidation gave back −0.081 on the two measured transitions.
Net D_select movement C1 → C3 was **+0.019**.

Mechanism: the consolidator promotes rules from `DynamicRules` into `BaseGuidelines` but
never removes them from `DynamicRules`, so the prompt ends up stating overlapping and
sometimes contradictory rules. Concretely in C2, base gained `"hard to tell" → rate 3` and
`"but"-clause dominates`, while `DynamicRules` kept `"Hard to find" + "works great" = 5`
and `Strong positive BEFORE "but" + minor complaint AFTER → 4-5`.

The gate could not catch it because it compared **val `CVaR_cluster`** of the consolidated
prompt against **D_select `cvar_lex` fitness** of the OE best, with `gate_delta = 0.01`:

| Cycle | best in OE (D_select) | consolidated (val CVaR) | threshold | verdict | true D_select effect |
|-------|----------------------|-------------------------|-----------|---------|----------------------|
| C1 | 0.5826 | 0.5767 | ≥ 0.5726 | pass by 0.004 | −0.0147 |
| C2 | 0.6127 | 0.6574 | ≥ 0.6027 | pass | −0.0665 |
| C3 | 0.5788 | 0.6233 | ≥ 0.5688 | pass | not measured |

Different splits *and* different metrics. C1 passed essentially by luck. The consolidated
prompt is never scored on D_select, which is exactly where the regression lives.

## 5. What worked as designed

**Significance-based anchor gate (M7/P6).** 0 rejections out of 3. Anchor accuracy of the
carried prompt rose 0.73 → 0.85 → 0.89, i.e. carried prompts genuinely lock in the
confidently-solved cells. Regression was diffuse (concentration 0.50 → 0.33 → 0.29), never
directional.

| Cycle | anchor acc before → after | improved / worsened | McNemar p (1-sided) | min detectable worsened |
|-------|--------------------------|---------------------|---------------------|-------------------------|
| C1 | 0.73 → 0.90 | 21 / 4 | 0.9999 | 5 |
| C2 | 0.85 → 0.87 | 8 / 6 | 0.788 | 5 |
| C3 | 0.89 → 0.90 | 8 / 7 | 0.696 | 5 |

**`group_aware` acquisition (O6).** Hard-slot error rate 52% → 76% → 86%; mean worker
disagreement on hard slots 0.056 → 0.087 → 0.127; hard slots covered 100% / 94% / 95% of all
seen errors; weak clusters (0, 1, 3) received 14 / 15 / 17 of 21 hard slots. Zero
representativeness warnings across all cycles.

**Pools.** seen 30 → 42 → 54 → 66 (12 added per cycle), unseen 470 → 434. The run therefore
only ever touched 13% of the 500-example acquisition pool. Pool-level `hard` markings grew
0 → 15 → 26, `anchor` 0 → 15 → 16.

## 6. Secondary defects found

1. **`R_worst` is unusable as a progress signal.** Exactly 0.500 on val in all three cycles.
   It is the 10th percentile of per-user accuracies, and with 8 reviews per user those
   accuracies are quantized to 1/8 steps, so the percentile barely moves. Raising caps to
   120 users did not help. Side effect: `proxy_validation.spearman` is `null` (zero variance).
2. **Mutator writes rules addressed to cluster ids.** C3 `DynamicRules` contain
   `CLUSTER 3 (Mixed/Lukewarm Reviews): ...`, but workers only see review text and cannot
   know the cluster. C3 was the only cycle where val CVaR fell (0.657 → 0.623).
3. **Val is evaluated twice per cycle.** `_eval_split` does not use `PredictionCache` (unlike
   `CandidateEvaluator`), so the consolidation gate and `12_selection_val` each spend
   960×3 = 2880 calls on the same prompt: ≈39 min of the 4 h run.
4. **Early-stopping exit saves the checkpoint synchronously.** C1 spent 356 s there; the
   max-iterations exit path takes under a second.

## 7. Where the 4 hours went

All of it is live ensemble inference (3 models, `max_parallel=8`, ~0.3–0.8 s per call).

| Stage | Total across run | Cost driver |
|-------|-----------------|-------------|
| OE evolution (14 iterations) | 68.9 min | D_select 240×3 = 720 calls per candidate |
| Consolidation (incl. its val eval) | 48.6 min | 960×3 = 2880 calls per cycle |
| Clustering (one-off) | 43.9 min | 140 users × 8 × 3 = 3360 calls with the seed prompt |
| Val selection | 39.1 min | another 2880 calls per cycle — duplicate of the above |
| Final OOD test | 12.5 min | 2880 calls |
| Fitness on D_select | 9.0 min | mostly cache hits after the first cycle |
| Anchor gate | 8.0 min | 100×3 per cycle, "before" side cached |
| Eval-set construction | 3.8 min | anchor candidate scoring |
| Data load + seen inference + pool expansion | 5.2 min | |

Per-cycle OE wall time decomposes exactly: C1 = 161 s seed + 757 s iterations + 356 s
checkpoint; C2 = 30 s + 1312 s + 1 s; C3 = 30 s + 1466 s + 0.4 s.
