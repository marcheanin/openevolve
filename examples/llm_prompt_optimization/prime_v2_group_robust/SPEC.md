## 1. Задача и мотивация (для нового читателя)

### 1.1 Постановка простыми словами

Есть замороженная LLM-система разметки: один или несколько LLM за API (менять веса
нельзя или невыгодно), общий текстовый промпт, задача классификации/аннотации.
Данные порождаются **разнородными источниками** — пользователями, авторами,
госпиталями, юрисдикциями, временными окнами. На деплое приходят **новые источники**,
не виденные при настройке (user shift в терминах WILDS, Koh et al., ICML'21).
Среднее качество приемлемо, но на худших источниках система проваливается — а
пригодность к деплою определяется именно хвостом (worst-group метрики).

**Цель (единственная, из неё выводится всё):** максимизировать качество на худшем
хвосте групп для не виденных при оптимизации источников, меняя только текстовый
промпт, при бюджете API-вызовов B.

### 1.2 Почему это не решается существующими методами

Две зрелые линии работ не пересекаются в нужной точке:

- **Дискретная оптимизация промптов** — APO/ProTeGi (EMNLP'23), OPRO (ICLR'24),
  EvoPrompt (ICLR'24), PromptBreeder (ICML'24), GEPA (ICLR'26), SPO (EMNLP'25),
  TextGrad, Reflexion — оптимизирует **среднюю** точность и никогда не
  проектировалась/не проверялась под distribution shift.
- **Group-robust обучение** — GroupDRO (Sagawa et al., ICLR'20), CVaR-DRO
  (Levy et al., NeurIPS'20), JTT (Liu et al., ICML'21), GEORGE (Sohoni et al.,
  NeurIPS'20), EIIL (Creager et al., ICML'21), PG-DRO (AAAI'23), AGRO — оптимизирует
  хвост, но **через веса модели** (reweight loss, дообучение), что для API-LLM
  недоступно. PfR (ICML'24) ближе всех: промптом предсказывает spurious-атрибут,
  но затем обучает сбалансированный классификатор — снова веса.
- Prompt-under-shift в vision (TPT, Any-Shift Prompting CVPR'24, DynaPrompt) —
  градиентные **soft**-промпты для CLIP, не дискретный текст.

Пересечение «дискретный промпт × групповая робастность» пусто — его и занимаем.

### 1.3 Мотивирующее свидетельство из наших же данных (v1)

Первая итерация проекта (PRIME v1, сабмишн ACL ARR May'26) — group-agnostic
эволюция промпта с active learning — показала на Amazon-WILDS: одномодельный
EvoPrompt даёт R_worst 56.50 против ансамблевого PRIME 55.91 — **на хвостовой
метрике generic-оптимизаторы неразличимы**, хотя по среднему различаются.
Причина системная: fitness v1 — глобальная точность, worst-group нигде не
оптимизируется. Слабость v1 становится мотивирующим результатом v2: generic prompt
optimization улучшает среднее, но не хвост. Подробный разбор v1 и рецензий — README §1–2.

## 2. Итоговый вклад статьи

**C1 (ядро).** Первая **group-robust дискретная оптимизация промпта**: CVaR/DRO-объектив
(Levy et al., NeurIPS'20) поверх **латентных, label-free выводимых групп** внутри
эволюционного поиска промпта (OpenEvolve/AlphaEvolve; MAP-Elites — Mouret & Clune'15).
Ключевая пара: эволюции безразлична негладкость и min-max природа DRO-объектива,
а промпту не нужны градиенты — недостатки взаимно гасятся.

**C2.** **Перенос latent group discovery из weight-space в prompt-space**: группы =
переносимые типы поведения источников (стиль письма, калибровка), выводимые из
label-free признаков (линия GEORGE/EIIL/JTT/PG-DRO, но без логитов и градиентов —
у API-LLM их нет). Группа — не только индекс для reweight, но и **семантика для
мутатора**: тип описуем текстом → style-conditional правила в промпте → правило
переносится на новых носителей типа без дообучения. Это рычаг, которого у
weight-DRO нет в принципе.

**C3.** **Архитектура ролей данных и бюджета для prompt-эволюции под хвост**:
разделение источников fit/heldout, четыре набора с непересекающимися ролями
(D_mut/D_select/D_anchor/U), каскад оценки, per-group Парето-фронт селекции
(огрубление per-instance фронта GEPA до групп). Отвечает инвариантам: тип-не-носитель,
хвост-не-среднее, бюджет-это-вызовы (§3.2).

**C4 (страховка/дополнение).** Первое **систематическое исследование** дискретных
prompt-оптимизаторов под сдвигом: {APO, OPRO, EvoPrompt, GEPA, SPO} × {среднее,
worst-group, ID→OOD gap}. Если E1-пилот не подтвердит метод (go/no-go), C4
становится ядром статьи (study-фрейминг), C1–C3 — честным negative/mixed result.

Не входит в contributions (осознанно): структурный промпт (механизм, не вклад —
абляция обязательна; **если** абляция structured-vs-monolithic покажет значимый
эффект на headline-метрике — повышается до вклада явно, Р15), ансамбль (наследие
v1, изолируется), label-lean (ветка с ослабленными гарантиями, §4.10).

**Иерархия claim'ов (для статьи, одним предложением):** ядро — «CVaR по label-free
выведенным группам внутри эволюции промпта улучшает worst-group OOD»; всё
остальное (роли данных, каскад, фронт, структура промпта) — заменяемая
инфраструктура, вклад которой измеряется лестницей E2, а не постулируется.

## 3. Формальная постановка и инварианты

### 3.1 Постановка

Единица сдвига (shift unit) u — то, что порождает коррелированные примеры и
меняется на деплое: user (Amazon-WILDS), identity-группа (CivilComments), госпиталь,
домен, временное окно. Дано: размеченный train с юнитами U_train; официальные
val/test с **новыми** юнитами; замороженный ансамбль f_1..f_M; бюджет вызовов B.

Выводим отображение юнитов в K латентных типов (label-free, §4.1). Цель:

    P* ∈ argmax_P  CVaR_q( {Acc_τ(P)}_{τ=1..K} )   при бюджете B,

где Acc_τ — точность на типе τ, CVaR_q — среднее по худшей q-доле типов (q≈1/3,
не строгий минимум — контроль шума). Официальная метрика бенчмарка (для Amazon —
10-й перцентиль точности по user_id) остаётся **внешним арбитром**; типы —
внутренний суррогат, чья корреляция с официальным хвостом проверяется (§4.1, E1).

### 3.2 Три инварианта (фильтр для каждого механизма)

- **I1 — тип, не носитель.** Всё оптимизируемое должно быть правилом про тип
  источника, не про конкретный источник. Механизм, способный вознаграждать
  запоминание конкретных рецензентов, дефектен.
- **I2 — хвост, не среднее.** Любой отбор (кандидатов, примеров, элитов) устроен
  так, чтобы прогресс на слабой группе не усреднялся прогрессом на сильных.
- **I3 — бюджет = вызовы API.** Дефицит — не метки (train размечен), а вызовы
  замороженного ансамбля. Тратить их там, где решение наиболее информативно.

## 4. Метод: компоненты и их взаимосвязь

### 4.1 Группы: label-free поведенческие типы

**Признаки юнита — два блока с разными правами (APPROACH_SLT §3.1):**

- **Блок T (transferable, доступен всегда, в т.ч. на unlabeled target):**
  средний эмбеддинг текстов юнита (sentence-transformer; PCA до 32–64 компонент,
  чтобы не подавить скаляры), статистики длины, дешёвые лексические маркеры
  (пунктуация, доля капса, восклицания), доменные метаданные, если есть.
- **Блок C (calibration, только на размеченном source):** средняя метка, дисперсия,
  доля экстремумов. **В геометрию кластеров не входит** — используется как внешняя
  валидация содержательности кластеров (ANOVA rating-статистик по кластерам)
  и для интерпретации.

**Fit и назначение (APPROACH_V3 §1.1):** k-means фитится **сразу в label-free
пространстве блока T**, только на fit-источниках (§4.3) — одна геометрия для
train/val/test/деплоя, двухпроекционная механика v2 упразднена (группы, не
распознаваемые label-free, не существуют на деплое — I1). StandardScaler
обязателен. Выбор K: silhouette + стабильность по сидам + **ограничение мощности**
K ≤ |D_select| / n_min. **n_min пре-регистрируется до просмотра данных** (Р9:
n_min=40) из worst-case биномиального CI: полуширина 95%-CI для Acc_τ ≤
1.96·√(0.25/40) ≈ 15.5 пп на отдельную группу; CVaR усредняет по ⌈K·q⌉ худшим
группам, снижая шум ещё в ~√⌈K·q⌉ раз. Критерий не подгоняется постфактум —
дисперсия внутри групп на него не влияет по построению (worst-case).

**Hard vs soft принадлежность — решено (§10, Р1).** Дефолт основного пайплайна
и E1 — **жёсткое назначение** (hard cluster id): пилот изолирует эффект
CVaR-объектива, лишний гиперпараметр (температура) там вреден, а проблемы, ради
которых SLT предлагает soft (пустые/крошечные кластеры, скачки CVaR), в v3 уже
закрыты Beta-сглаживанием (§4.4) и ограничением мощности при выборе K.
**Soft-membership π_u(τ) = softmax(−dist²/T_temp)** (SLT; интуиция PG-DRO:
пересекающиеся failure modes) — оформленный апгрейд, строго обобщающий hard
(hard = предел T_temp→0; Beta-сглаживание обобщается на эффективные счётчики
n_τ = Σπ). Критерий перехода на soft: (а) диагностика показывает нестабильные
или крошечные кластеры, или (б) soft-арка выигрывает на val в абляции E6.

**Текстовые дескрипторы типов (APPROACH_SLT §3.4):** после fit для каждого τ —
top-N ближайших юнитов + шаблонный дескриптор («краткие отзывы с гиперболами,
путают 3 и 4»); попадает в артефакты мутатора и в заготовки style-conditional
правил. **Решено (§10, Р4): дескрипторы — в основном конфиге**, строятся только
из nearest neighbors + шаблона; LLM-редактор дескрипторов опционален и
абляируется (риск галлюцинаций).

**Почему элемент кластера — пользователь (юнит), а не отзыв.** (1) Ось сдвига и
официальная метрика живут на уровне юнита: на тесте приходят новые *авторы*;
правило «для типа автора» переносится, кластер отзывов — нет. (2) Защита от
группировки по метке (I1): кластеры отдельных отзывов выучивают оси сентимента
(«сердитый короткий» ≈ класс 1–2) — CVaR выродился бы в per-class accuracy;
агрегация по юзеру усредняет его отзывы разных классов, оставляя стабильные
поведенческие черты. (3) Статистика: профиль = среднее n_u отзывов, шум ↓ 1/√n_u.
Смягчения известных рисков: юзеры с n_u < `min_reviews_for_fit` (=3) не участвуют
в fit k-means (назначаются к готовым центроидам); внутрипользовательская дисперсия
(средняя дистанция отзывов юзера до его профиля) логируется при fit — высокая доля
«размазанных» юзеров = триггер soft-абляции (Р1); ошибки назначения ограничены по
ущербу: мутатор пишет правила из текстов (не из номеров кластеров), а в режиме A
кластеры на инференсе не используются вовсе.

**Прокси-валидация как гейт с ремонтом (V3 §1.1):** corr(CVaR_cluster, R_worst_val)
логируется каждый цикл; если после N циклов ниже порога — **остановка и перефит**
(другое K/признаки), а не продолжение дорогой эволюции по бессмысленным осям.
Численный порог гейта фиксируется после первых данных (Фаза 4; Р10) — до данных
это было бы новое магическое число; в E1 — только логирование.

**E0 — почти бесплатная диагностика корреляции до E1 (Р12).** Назначение кластеров
не меняет предсказаний ансамбля, поэтому **один** прогон стартового промпта на
val даёт corr(CVaR_cluster, R_worst) сразу для всех K и вариантов признаков —
переиспользуем предсказания, пересчитывая только группировку. Если корреляция
мертва при любом K, мы узнаём это за один инференс, а не за $30 пилота (§7/E0).

### 4.2 Ансамбль и сигналы

Ансамбль v1 сохраняется без изменений (изоляция вкладов): gpt-4o-mini,
gemini-2.5-flash, claude-3.5-haiku; мутатор — отдельная модель. Изменения v3:

- **Агрегация — медиана** голосов (для порядковой 5-балльной шкалы медиана
  состоятельна и не требует магического тай-брейка); majority vote — абляция.
- **κ (согласие воркеров) исключён из fitness** — он удовлетворяется деградацией
  (промпт, продавливающий всех к «3», получает высокий κ; циркулярность отметили
  и рецензенты v1). Остаётся диагностикой коллапса ансамбля в логах.
- **d_i (несогласие по примеру)** — label-free сигнал информативности
  (Query-by-Committee, Seung et al., 1992). Зависит от текущего промпта, поэтому
  используется только в короткоживущих решениях (минибатчи мутатора, подпитка
  из U), никогда — в персистентных наборах.

### 4.3 Роли данных (ядро ревизии v3; упраздняет AL-пул v1/v2)

Мотив: Seen/Unseen/Hard/Anchor-машинерия v1 проектировалась под дефицит **меток**,
а наш дефицит — **вызовы** (I3). Один активный батч (~80) выполнял четыре
несовместимые роли (сигнал мутатору / fitness / оси архива / регрессионный якорь) —
и ни одну хорошо: Goodhart на 80 примерах, несравнимость fitness между циклами,
Acc_k, занижённый hard-квотами, поверх которого считался CVaR.

**Разбиение по источникам:** train-источники делятся на `fit_sources`
(кластеризация, минибатчи мутатора) и `heldout_sources` (селекция) — **70/30 по
user_id** (Р7), сид в конфиге, user-disjoint проверка. Разбиение
**стратифицируется** по профильным признакам юнитов (квантили длины, первая
PCA-компонента эмбеддинга), чтобы половины не получили собственный систематический
сдвиг (Р15); остаточный дисбаланс логируется при построении, а его эффект ловится
внутренним ID-vs-OOD-логом (§4.8). Это внутренняя репетиция деплоя: правило
выучено, только если работает на *других носителях того же типа* (I1). Размеры
наборов (Р9): полный ран — |D_select|=400, |D_anchor|=100, |D_mut|=35; capped
E1 — 200/50/30. D_anchor ⊂ heldout, дизъюнктен с D_select. Ограничение мощности:
n_min=40 → K ≤ |D_select|/40 (на capped-ране автоматически меньше групп, а не
более шумные оценки).

| Набор | Состав | Обновление | Роль | Допустимое смещение |
|---|---|---|---|---|
| **D_mut** | 30–40 прим. из fit_sources; квоты ∝ (1−Acc_τ), ранг (err, d), diversity | заново на каждую мутацию | error artifacts мутатору + локальный тест «лучше родителя?» | адверсариальное — желательно |
| **D_select** | 300–500 прим. из heldout_sources, стратификация по группам (назначение label-free) | фиксирован на ран | fitness, CVaR, дескрипторы QD, Парето-фронт, carryover | никакого |
| **D_anchor** | ~100 прим., ячейки группа×класс из уверенно решённых | фиксирован на ран | регрессионный гейт при приёмке (CI/δ-допуск, Р15) | консервативное |
| **D_audit** | ~50–100 прим. из heldout, дизъюнктен с D_select/D_anchor | фиксирован на ран | редкая (раз в цикл) независимая оценка: разрыв D_select↔D_audit = мера post-selection bias | никакого; **никогда** не участвует в селекции |
| **U** | неразмеченный резервуар | по требованию | подпитка D_mut по d_i (label-lean) | — |

Зачем D_audit (Р15): D_select фиксирован ради сравнимости fitness между циклами,
но многократный отбор кандидатов по одному набору создаёт post-selection bias,
который бутстрэп не лечит. Рефреш D_select ломал бы сравнимость; вместо этого
держим нетронутый аудит-срез: рост разрыва D_select↔D_audit — прямой индикатор
оверфита селекции, D_audit при этом ничего не решает (nested-validation дёшево).

Каждая эвристика v1/v2 переезжает туда, где её смещение полезно: групповые квоты
и (err,d)-ранжирование → только D_mut; стратификация → D_select; anchor-идея →
отдельный гейт вместо 30% разбавления батча; expansion по d_i → подпитка D_mut.
Acc_τ для квот D_mut берётся с D_select (несмещённая оценка слабости групп).

**Каскад бюджета (I3):**
1. Мутация → оценка на своём D_mut (~35×M вызовов). Хуже родителя → отброс.
2. Прошёл → шард D_select (25–33%). Вне зоны фронта (с учётом CI) → отброс.
3. Выжил → полный D_select + гейт D_anchor → запись в архив/фронт.
   Гейт якоря — **не строгий no-regression, а CI/δ-допуск** (Р15): уверенно
   решённые примеры могут опираться на ложные корреляции, и жёсткий фильтр
   отклонял бы мутации, спасающие худшую группу ценой ~нуля на якоре. Счётчик
   «отклонено якорем» пишется в логи — по нему видно, блокирует ли гейт полезное.

Полную оценку получают ~10–20% кандидатов; сэкономленное → больше мутаций.
Кэш (sha256(prompt), example_id) → prediction: при T=0 воркеры детерминированы,
повторные оценки бесплатны.

### 4.4 Fitness

Скаляр для OpenEvolve — **лексикографическая аппроксимация** (не магическая смесь):

    fitness = CVaR_shrunk + ε·Acc_global − penalty_len,   ε ≈ 0.01 (тай-брейк)

- **Сглаживание:** Acc_τ = (correct_τ + a)/(n_τ + a + b), Beta-prior a=b=1;
  CVaR по сглаженным значениям; в логах бутстрэп-CI. (В soft-абляции —
  эффективные счётчики n_τ = Σπ.)
- **length_penalty** сохраняется с новой мотивировкой: не только стоимость, но и
  OOD-регуляризатор (длинный промпт = много узких правил = оверфит на источники
  оптимизации).
- Режимы `global` и `v1_weighted` (0.5·AccHard+0.3·AccAnchor+0.2·κ) остаются
  **только как абляционные арки E1/E2**.

### 4.5 Эволюция и структурный промпт

Внутренний цикл — OpenEvolve (LLM-мутатор + архив), линия
AlphaEvolve/FunSearch/EvoPrompt. Мутатор получает: per-type ошибки с D_mut,
дескрипторы типов (§4.1), **changelog правил линии предков** (какие правила когда
добавлены и какую группу чинили — прямой аналог накопленных уроков GEPA) и право
писать **style-conditional правила** («если отзыв краткий и гиперболизированный —
проверь сарказм, прежде чем ставить максимум»).

**Структурный промпт — механизм, не вклад** (позиция README §5.5 + APPROACH §4.3):
- `<BaseGuidelines>` — групп-инвариантное ядро, медленная шкала, правится только
  консолидацией;
- `<DynamicRules>` — носитель type-conditional правил, быстрая шкала;
- `<FewShotExamples>` — стилевые примеры-двойники под худшие группы (синтетика
  получает стиль группы как спецификацию; абляция на headline-метрике — урок v1);
- **Структурный валидатор мутаций (V3 §1.5):** после мутации — diff по блокам;
  изменение >1 блока, порча тегов, правка BaseGuidelines вне консолидации →
  отклонение **до всякой оценки** (0 вызовов — самый дешёвый фильтр). Дисциплина
  через энфорсмент, а не через пожелание в system message.
Claim про «catastrophic forgetting in prompt space» в статье не делается, пока
абляция structured-vs-monolithic его не подтвердит.

### 4.6 QD-архив и per-group Парето-фронт

- **Дескрипторы архива** — сглаженные Acc_τ с шарда/полного D_select, feature_bins=3
  (слабая/средняя/сильная) — ячейка означает «профиль специализации», а не шум.
  MAP-Elites-сетка — реализация хранения; при K=8 и bins=5 сетка была бы 5⁹ ячеек
  на популяцию в десятки — честнее проектировать как разреженный словарь.
- **Первичная структура селекции — per-group Парето-фронт** (GEPA per-instance,
  огрублённый до групп, потому что группы — ось задачи):
  - кандидат живёт во фронте, если лучший (или в CI лучшего) хотя бы на одной
    группе по D_select;
  - родитель следующей мутации сэмплируется с фронта с весом ∝ числу групп, где
    он лидирует (I2: специалист по слабой группе размножается, даже если его
    средний fitness низок);
- **Carryover между циклами** = срез фронта (элита на группу + глобальный лучший,
  3–5 промптов), все fitness измерены на одном и том же D_select — сравнение
  корректно по построению. Одноточечное бутылочное горлышко v1 (архив сбрасывался,
  переходил один промпт) устранено.

**Разделение труда фронта и скаляра (не противоречие, а два уровня):** скаляр
§4.4 — интерфейсное требование OpenEvolve во внутреннем цикле (архиву нужен один
float) и тай-брейк при прочих равных; фронт — логика **приёмки, выбора родителя
и carryover**. Решения фронта скаляр не отменяет никогда. Открытым остаётся
только инженерный вопрос интеграции с parent selection OpenEvolve — он закрыт
прототипом-спайком в начале Фазы 3 (до E2) и fallback'ом §8.3.

### 4.7 Консолидация

Консолидация = LLM-слияние комплементарных правил специалистов в BaseGuidelines.
Правила: scope — только BaseGuidelines; консолидат — **кандидат, не наследник**
(эволюция сама поднимет, если хорош); оценивается каскадом на D_select как обычный
кандидат; гейт **CI-aware** (принять, если нижняя граница CI консолидата не хуже
верхней границы CI лучшего − δ) + D_anchor-гейт.

### 4.8 Иерархия оценки и сертификация

Градиент стоимости и полномочий — ни один уровень не подменяет другой:

| Уровень | Частота | Данные | Решение |
|---|---|---|---|
| D_mut | каждая мутация | fit_sources, адверсариальный срез | жив/мёртв локально |
| D_select (шард → полный) | каждый выживший | heldout_sources, стратифицирован | фронт, архив, carryover |
| Официальный val (WILDS OOD) | раз в AL-цикл | новые источники | межцикловой выбор; прокси-гейт кластеров |
| Официальный test | один раз | новые источники | сертификация: R_worst, CVaR, бутстрэп-CI, ID-vs-OOD gap |

Внутренний ID-vs-OOD gap (fit_sources vs heldout_sources на D_select) логируется
каждый цикл — ранний детектор оверфита на источники оптимизации. Раз в цикл
оценивается D_audit (§4.3) — разрыв D_select↔D_audit = мера post-selection bias.

**Таблица информационного доступа (Р15; в статью — вместе с algorithm box):**

| Компонент | Видит | Не видит |
|---|---|---|
| Мутатор (LLM) | тексты и ошибки D_mut (fit_sources), дескрипторы типов, changelog предков | любые примеры heldout (D_select/D_anchor/D_audit), val, test |
| Селекция (каскад, фронт, carryover) | **только агрегаты** по D_select: сглаженные Acc_τ, CVaR, CI | тексты D_select (в контекст LLM не попадают никогда) |
| Межцикловой выбор промпта | агрегаты официального val | test |
| Сертификация | test, один раз | — |

Ответы на протокольные вопросы, которые задаст рецензент: оптимизатор видит из
heldout только числа-агрегаты; один и тот же пример D_select участвует в селекции
многократно (каждый выживший кандидат), но никогда — в генерации правок; смещение
от повторного отбора измеряется D_audit и ограничивается официальным val-арбитром
и замороженным test.

### 4.9 Спектр маршрутизации A/B/C

Как донести групповые правила до инференса — отдельная исследовательская ось:
- **A (дефолт):** один промпт, условные правила по наблюдаемым признакам текста;
  LLM роутит сам; группа на тесте не нужна.
- **B (главный претендент):** общая база + подставляемый блок DynamicRules
  группы k; юнит назначается label-free роутером (после V3 §1.1 роутер работает
  ровно в пространстве fit'а — рассинхрон исчез по построению). Страховки:
  abstention-fallback на генералистский промпт при большом расстоянии до центроида;
  порог данных на выделение блока; оценка только с **предсказанным** роутингом.
- **C (абляция):** K независимых промптов + роутер (mixture-of-prompts).
Ключевой риск явного роутинга: ошибки роутера концентрируются на атипичных
источниках — ровно на оптимизируемом хвосте. Порядок: A — дефолт, B — после E1
и внедрения ролей данных (Фаза 3).

### 4.10 Label-lean режим

Отдельная экспериментальная ветка с **явно ослабленными гарантиями** (без меток
невозможен несмещённый D_select): селекция по d_i-прокси + крошечный размеченный
D_select из десятков примеров. Основная архитектура проектируется под «метки train
есть, вызовы дороги». Родственные работы: SPO (EMNLP'25, LLM-judge pairwise),
PDO (dueling bandits), Dynamic Cheatsheet (EACL'26, label-free память + куратор).

### 4.11 Цепочка «цель → компонент» (связность)

1. Деплой-метрика — хвост групп на новых источниках → группы распознаваемы без
   меток → label-free fit кластеров (§4.1).
2. Правила должны обобщаться на новых носителей типа (I1) → D_select из отложенных
   источников (§4.3) — условие деплоя воспроизведено внутри цикла.
3. Оптимизируется хвост (I2) → CVaR по сглаженным Acc_τ на D_select, lex-тай-брейк
   (§4.4); эволюции безразлична негладкость — пара «DRO × эволюция» и есть ядро C1.
4. Прогресс на слабой группе нельзя усреднить (I2) → per-group Парето-фронт (§4.6).
5. Мутатору нужно знать, где болит → D_mut: свежий адверсариальный срез слабых
   групп + артефакты + changelog (§4.3, §4.5) — смещение здесь работает на нас.
6. Починка группы k не должна ломать группу j → scoped-мутации с энфорсментом +
   двухшкальный промпт + D_anchor-гейт — три независимых механизма изоляции.
7. Специалистов сливать, не теряя → консолидация только базы, CI-aware гейт (§4.7).
8. Бюджет — вызовы (I3) → каскад + кэш (§4.3).
9. Финальное слово — официальные val (арбитр) и test (одна сертификация) (§4.8).

Удалено без замены (и почему): κ из fitness (удовлетворяется деградацией);
магическая смесь весов (противоречила собственной lex-логике); Seen/Unseen/
Hard/Anchor-пул (решал дефицит меток, которого нет); full-проекция кластеров
(группы, не распознаваемые label-free, не существуют на деплое); 30%
anchor-разбавление батча (слабая форма настоящего регрессионного гейта);
бинарный префильтр err/d; majority+tie-break (медиана состоятельнее для
порядковой шкалы).

## 6. Датасеты и протокол оценки

### 6.1 Amazon-WILDS (основной стенд)

- Задача: 5-way sentiment (звёзды) по тексту отзыва; сдвиг — по рецензентам
  (test-юзеры не встречаются в train). **Только официальные** train/val/test
  OOD-сплиты WILDS (Koh et al., ICML'21) — кастомный 70/15/15-сплит v1 был
  главным протокольным дефектом (сравнение с лидербордом было некорректно).
- Официальная headline-метрика: **R_worst = 10-й перцентиль точности по юзерам**;
  дополнительно R_global, MAE. Внутренний суррогат CVaR_cluster валидируется
  корреляцией с R_worst (§4.1).
- Внутри train — source-level разбиение fit/heldout (§4.3). Кластеры фитятся
  только на fit-источниках.

### 6.2 CivilComments-WILDS (второй бенчмарк, согласован)

- Токсичность, **oracle-группы** = identity-атрибуты; официальная метрика —
  worst-group accuracy. Метод работает в oracle-режиме (кластеризация не нужна —
  подключаемость модуля групп демонстрируется явно: oracle на CivilComments,
  inferred на Amazon). Прямое сравнение с PfR (ICML'24). Другой класс-баланс —
  смоук обязателен до полного прогона.

### 6.3 Category shift внутри Amazon (третья ось, почти бесплатно)

Эволюция на Books-heavy пуле → тест на прочих категориях: второй тип сдвига
без нового датасета (E10).

### 6.4 Статистический протокол (единый для всех экспериментов)

- 3 сида для headline-чисел; mean±std; **paired bootstrap по юзерам** на общем тесте.
- Все выборы гиперпараметров — по val, никогда по test; test — один раз (§4.8).
- Бюджет B — первоклассный конфиг; вызовы логируются по уровням каскада,
  **включая вызовы официального val и прокси-гейта** (Р12);
  mutator-токены измеряются, не оцениваются (замечание рецензента v1).
- ID-vs-OOD gap репортится для каждого метода (наш и baselines).

### 6.5 С чем и как сравниваем — сводная матрица

Зачем каждая семья baselines и что именно она проверяет:

| Семья | Методы | Что проверяет | Где | Протокол |
|---|---|---|---|---|
| Без оптимизации | zero-shot, hand-crafted промпт, few-shot ICL | нижняя планка; «бьёт ли оптимизация вообще ручной промпт» | Amazon, CivilComments | тот же ансамбль/агрегация |
| Generic prompt-оптимизаторы | EvoPrompt, APO/ProTeGi, OPRO (готовы из v1), GEPA, **MIPROv2 (DSPy, Р14)** | ядро тезиса: улучшают среднее, но не хвост | Amazon (E3), оба (E9) | **равный бюджет вызовов B**, тот же стартовый промпт, официальные сплиты, метрики: R_global, R_worst, ID→OOD gap |
| Label-free оптимизаторы | SPO | baseline для label-lean ветки | Amazon | label-budget кривая |
| Group-robust промпт-стиль | PfR-style промпт (предсказание атрибута промптом) | ближайший идейный сосед в prompt-space | CivilComments (E4) | oracle-группы, их протокол |
| Fine-tuning (справочно) | ERM, GroupDRO, LISA (лидерборд WILDS); LoRA Qwen3-8B (вторичная ветка) | контекст «prompt vs weights»; не headline-claim (урок v1) | Amazon | официальный тест; LoRA — равные N меток |
| Внутренние контроли | global-fitness арка (E1), random-clusters (Р13), лестница E2 | фальсификация: эффект от групп или от структуры объектива | Amazon | те же раны, 1 отличие на арку |

Правила честного сравнения (сводно): один стартовый промпт для всех оптимизаторов;
равный бюджет B (замер TokenTracker'ом, не оценка); официальные OOD-сплиты; выбор
финального кандидата у каждого метода — по его собственному val-критерию (не по
нашему); все хвостовые метрики с bootstrap-CI; ID→OOD gap считается для каждого
метода одинаково (E5).

## 7. План экспериментов

Формат: цель → дизайн → критерий → бюджет/фаза кода (§8).

### E0 — диагностика прокси (до E1, почти бесплатно; Р12)

- **Цель:** валидны ли выбранные группы как суррогат официального хвоста —
  до того, как жечь бюджет на эволюцию.
- **Дизайн:** один прогон стартового промпта на val (capped); по одним и тем же
  предсказаниям пересчитываются группировки для сетки K и вариантов признаков
  (`full_T`, `emb_only`, `pred_profile`, `shuffle`); разброс по сидам кластеризации.
- **Критерий (обновлено после large-cap / OBSERVATIONS P1):** primary —
  **permutation Kruskal–Wallis** по per-user accuracy × cluster
  (p < 0.05 и H бьёт shuffle). LOO Spearman — только диагностика (смещён под
  нулём). Есть значимый K → E1 с этим K/признаками. Null на large-cap →
  чинить признаки до E1 или study-фрейминг.
- **Бюджет:** один инференс val-capped (~600×M–1200×M вызовов); Фаза 1.
  Сохранять `val_predictions.npy` **и** `val_worker_predictions.npy`.

### E1 — пилот go/no-go (первым после E0, Фазы 0–1)

- **Цель:** двигает ли CVaR-объектив хвост. Единственное отличие арок:
  fitness `cvar_lex` vs `global`; всё остальное зафиксировано.
- **Группы (после E0 large-cap):** default geometry = **`pred_profile`**
  (K=6; fit на seed-prompt preds fit-источников). Style/`full_T` — ablation.
  См. `experiments/OBSERVATIONS.md` C6/P4 и
  `experiments/E1_pred_profile_cvar_vs_global/`.
- **Дизайн:** 1 сид, официальный сплит, capped test, равный бюджет.
- **Критерий (Р11, ужесточён после внешнего ревью):** primary — **официальный
  R_worst на val**; test — только подтверждение. **Go** = CVaR-арка > global по
  R_worst_val. Выигрыш только по CVaR_cluster без выигрыша по R_worst =
  **weak-go**: не успех, а сигнал «суррогат оторван от цели» — сначала ремонт
  прокси (K/признаки, диагностика E0), потом повтор. **No-go** по обеим →
  study-фрейминг (E9 ядром), C1–C3 — negative result. Бюджет ≈ $25–30, 6–9 ч.
- **Важно (V3):** проводится только после внедрения ролей данных — E1 на
  батч-машинерии v2 измерял бы шум батча, не эффект объектива. Прогонов E1 ещё
  не было (подтверждено, §10 Р2): существующие конфиги и live-скрипты E1
  мигрируются на v3 до первого запуска. Семантика Фаз 0–1 в E1 (Р6): батч-механизм
  остаётся только кормом мутатора; fitness/селекция — с D_select (capped: 200,
  D_anchor 50, K ≤ 5 по правилу мощности).

### E2 — компонентная лестница (главная таблица статьи)

- **Цель:** вклад каждого компонента на headline-метрике (ответ на критику v1
  «абляции на прокси-метриках»).
- **Арки (переопределены под v3-архитектуру, состав подтверждён — §10 Р5):**
  1. zero-shot стартовый промпт;
  2. plain evolution: global fitness, случайные минибатчи, без групп;
  3. + group-weighted D_mut (квоты ∝ 1−Acc_τ);
  4. + CVaR_lex fitness;
  5. + групповые артефакты и style-conditional правила;
  6. + per-group Парето-фронт и carryover;
  7. + консолидация с CI-гейтом и D_anchor (= полный GRAPE).
- **Дизайн:** официальный тест, 3 сида, paired bootstrap.

### E3 — baselines при равном бюджете

EvoPrompt, APO, OPRO (перегнать v1-реализации на официальном сплите), GEPA
(код открыт), **MIPROv2 из DSPy (Р14 — де-факто индустриальный стандарт
оптимизации промпта под кастомную метрику; его отсутствие вызовет вопросы)**,
few-shot ICL, zero-shot, PfR-style промпт; справочно ERM/GroupDRO/LISA с
официального лидерборда (теперь сравнение честно). Равный бюджет вызовов.
Полная матрица сравнения и правила честности — §6.5.

### E4 — CivilComments-WILDS

Oracle-группы; сравнение с PfR; демонстрация подключаемости модуля групп.
Смоук → полный прогон. **Арка inferred-vs-oracle (Р15):** дополнительно
запускаем SLT-кластеризацию, игнорируя oracle-метки групп, и сравниваем
worst-group метрики «оптимизация по inferred» vs «по oracle» — прямой тест
переносимости C2 (иначе CivilComments проверяет только объектив, а не
discovery, и это ограничение прописывается в тексте статьи явно).

### E5 — ID-vs-OOD gap

Каждый финальный промпт (наш и E3) оценивается на held-out отзывах train-юзеров
и на test-юзерах. Гипотеза: у generic-оптимизаторов gap больше. Дёшево (промпты
уже есть), убедительно. Внутрицикловая версия — в каждом ране автоматически (§4.8).

### E6 — чувствительность (закрывает «новые магические числа»)

K ∈ {4, 8, 12}; CVaR-квантиль ∈ {25%, 33%, 50%}; soft-арка с T_temp-сеткой
(критерий принятия soft — §4.1); параметры сглаживания. 1 сид, capped;
выбор — только по val. Отдельно документируется вырождение на малых K:
при K=4 и q=1/3 «худшая треть» — это одна группа, CVaR превращается в строгий
минимум со всем его шумом (ожидаемый провал этой ячейки сетки — не баг, а
иллюстрация, почему нужен запас по K).

### E7 — качественный анализ

Возникшие style-conditional правила; per-group confusion до/после; история
эволюции и changelog; интерпретируемость как преимущество перед невидимым
reweight weight-DRO.

### E8 — статистика

Paired bootstrap по юзерам; вариативность между сидами; отчёт CI для всех
headline-чисел (замечание рецензента v1: выигрыш 1.2 пп при шуме 0.5–1.0 пп
не защищается без этого).

### E-абляции механизмов (1 сид, capped; победители → основной конфиг)

- **random-clusters контроль (фальсификация, обязателен; Р13):** случайная
  перестановка назначений юнит→группа при том же K и том же пайплайне.
  Если CVaR по случайным группам даёт тот же прирост, что по выведенным, —
  групповая гипотеза неверна (эффект от структуры объектива, не от групп).
  Это «одна абляция, которая обрушит метод, если теория неверна»;
- structured vs monolithic промпт (§4.5);
- carryover: collapse-to-one (v1) vs пул vs per-group фронт (§4.6);
- median vs majority агрегация (§4.2);
- структурный валидатор on/off (счётчик отклонённых мутаций — почти бесплатно);
- дескрипторы типов: шаблон (дефолт) vs шаблон+LLM-редактор vs без.

### E-routing — спектр A/B/C (после Фазы 3)

A vs B vs C при равном бюджете; только предсказанный роутинг; качество роутера
логируется отдельно; у B — abstention-fallback. Вопрос эксперимента: «сколько
явной маршрутизации нужно робастности в prompt-space».

### E9 — систематическое исследование (study-фрейминг: страховка или ядро)

{APO, OPRO, EvoPrompt, GEPA, SPO} × {Amazon, CivilComments} × {avg acc,
worst-group, ID→OOD gap}. Тезис: оптимизаторы улучшают среднее, не хвост,
и оверфитятся на распределение оптимизации. Цитируемый результат сам по себе.

### E10 — category shift

Эволюция на Books-heavy → тест на прочих категориях; тот же пайплайн.

### Вторичные ветки (по бюджету)

- **Label-budget кривая:** N gold ∈ {0, 25, 100, 400}; при N=0 — label-lean ветка
  (§4.10); baseline SPO. Раздел, не headline.
- **LoRA на Qwen3-8B:** (а) zero-shot, (б) +наш промпт, (в) LoRA на тех же N
  метках, (г) LoRA на полном train — честная версия «prompt vs weights» вместо
  снятого клейма v1 про DistilBERT-LISA.

### Смета бюджета (предварительная; Р12 — вызовы val/гейтов входят в B)

Один AL-цикл полного рана (M=3 воркера, ~30 мутаций/цикл, до кэша):

| Уровень | Расчёт | Вызовов |
|---|---|---|
| D_mut (каждая мутация) | 30 × 35 × 3 | ~3 200 |
| Шард D_select (~30% выживших) | ~9 × 130 × 3 | ~3 500 |
| Полный D_select (~10–20%) | ~4 × 400 × 3 | ~4 800 |
| D_anchor-гейт | ~4 × 100 × 3 | ~1 200 |
| Официальный val (раз в цикл) | 600 × 3 | ~1 800 |
| D_audit (раз в цикл) | 100 × 3 | ~300 |
| **Итого/цикл** | | **~15 000** |

Capped E1 (200/50/30, val 600, 3 цикла, 2 арки) — ориентир ~55–60k вызовов на
арку ≈ $25–30 (сверка с фактом v1: полный ран ~$27 / 41M токенов). Кэш
(sha256(prompt), example_id) снижает повторные полные оценки (carryover-промпты
переоцениваются бесплатно). Если смета не сходится — первым сокращается частота
полных оценок D_select (§9, риск 3). Факт по уровням пишет TokenTracker; смета
обновляется после E1 фактическими числами.

### Порядок работ

1. Фазы 0–1 кода (§8) — без LLM-затрат.
2. **E0** (один инференс val) → фиксация K и признаков.
3. E1 → решение о фрейминге (критерий Р11).
4. Дешёвые E-абляции (включая random-clusters) → зафиксировать конфиг.
5. E2 + E3 (официальный тест, 3 сида); прототип-спайк фронта — до E2 (§4.6).
6. E4, E5, E6–E8.
7. E-routing (после Фазы 3); E9–E10 и вторичные ветки — по бюджету и результату E1.

## 8. Реализация

### 8.1 Текущее состояние (`prime/`, детали — IMPLEMENTATION.md)

Реализован v2-скелет: официальные WILDS-сплиты с кэшами; профили юнитов и k-means
с сериализацией; CVaR-метрики и конфигурируемый fitness; лексикографический
scoring; top-k+diversity батчер; per-cluster артефакты мутатора; pool_carryover
с cluster_pareto-опцией; bootstrap-статистика; OpenEvolve-адаптер; E1-конфиги и
smoke-валидация всех стадий. **Скелет соответствует v2 и требует миграции на v3.**

### 8.2 План миграции (APPROACH_V3 §3, сводно)

- **Фаза 0 — гигиена:** режим `cvar_lex`; κ убрать из всех режимов кроме
  `v1_weighted`; Beta-сглаживание + CI в metrics; агрегатор `median`;
  удалить мёртвый `CandidateEvaluator._run_predict`; `base_v3.yaml`.
- **Фаза 1 — роли данных:** `data/splits.py` (fit/heldout-источники, 70/30,
  стратификация по профильным признакам); label-free fit кластеров + отчёт
  внешней валидации по rating-статистикам; ограничение мощности в выборе K;
  `acquisition/eval_sets.py` (D_select, D_anchor, **D_audit** — сериализуются
  в run_dir, неизменны в течение рана); `CandidateEvaluator` v3:
  `evaluate_mut`/`evaluate_select`, файловый кэш предсказаний;
  `experiment/budget.py` (TokenTracker по уровням каскада, включая val/audit);
  **скрипт E0** (`scripts/run_e0_proxy_diag.py`).
- **Фаза 2 — перекоммутация цикла:** убрать AcquisitionPool.hard/anchor;
  D_mut per-мутация (квоты от сглаженных Acc_τ с D_select); каскад приёмки
  (через `cascade_evaluation` OpenEvolve или обёртку адаптера) с CI/δ-гейтом
  якоря и счётчиком отклонений; QD-дескрипторы от D_select, bins=3; внутренний
  ID-vs-OOD лог + оценка D_audit раз в цикл; флаг random-clusters контроля
  (`clusters.control: none|shuffle`).
- **Фаза 3 — селекционные структуры:** `pareto_front.py` (CI-aware приёмка,
  веса сэмплирования родителя); структурный валидатор мутаций
  (`prompt_blocks.py`); консолидация каскадом + CI-гейт; changelog в артефакты.
- **Фаза 4 — протокол:** бюджет B в конфиге + TokenTracker по уровням каскада;
  прокси-гейт кластеров со стоп-кодом; label-lean как изолированная ветка;
  тесты (`test_eval_sets`, `test_pareto_front`, `test_mutation_validator`,
  обновить `test_clustering` под label-free fit).
- Для soft-абляции (E6): `profiles.features_transferable/calibration`,
  softmax-π в clustering, weighted Acc_τ в metrics, вес ∝ Σπ(τ)(1−Acc_τ)
  в acquisition (план APPROACH_SLT §8). Реализуется после E1, не блокирует пилот.

### 8.3 Fallback интеграции

Если per-group фронт поверх parent selection OpenEvolve окажется инвазивным —
серия коротких OpenEvolve-ранов с нашей селекцией между ними (архитектурно уже
поддержано AL-циклами).

## 9. Риски

1. **E1 no-go** (~30–40%): CVaR на суррогатных группах не двигает официальный
   хвост. Смягчение: кластеры вместо юзеров (статистическая мощность), сглаживание,
   прокси-гейт с ремонтом. План Б встроен: study-фрейминг (C4 ядром).
2. **Кластеры не захватывают ось сдвига** (сдвиг в калибровке, не в стиле) —
   label-free fit сознательно исключил rating-сигнал из геометрии (плата за I1);
   внешняя валидация по блоку C покажет потерю содержательности; E6 проверяет K.
3. **Стоимость D_select:** 300–500×M на выжившего кандидата; компенсируется
   каскадом и кэшем; при несходимости бюджета первым сокращается частота полных
   оценок.
4. **Effect size 1–2 пп** → без 3 сидов и bootstrap не защищается; бюджет на
   повторы заложен заранее.
5. **Меньше данных кластеризации** из-за выделения heldout-источников — конфликт
   с выбором K лечится порогом мощности (§4.1).
6. **Интеграционные затраты GEPA/SPO-baselines** — минимум EvoPrompt/APO/OPRO
   (готовы из v1) + ICL; GEPA — в E9.
7. **Сложность фронта поверх OpenEvolve** — fallback §8.3.

## 10. Лог принятых решений (бывшие открытые вопросы; зафиксировано с автором)

- **Р1 — группы: hard-дефолт, soft-апгрейд.** Основной пайплайн и E1 — жёсткое
  назначение кластеров; soft-membership (SLT) — абляция E6 со строгим критерием
  принятия (§4.1). Обоснование: пилот изолирует объектив, температура — лишний
  гиперпараметр в go/no-go; шум и мелкие кластеры уже закрыты сглаживанием и
  порогом мощности K.
- **Р2 — E1 не гонялся.** Существующие конфиги/скрипты E1 мигрируются на
  v3-роли данных до первого запуска; первые результаты E1 будут сразу валидными.
- **Р3 — имя.** Метод в статье — GRAPE; SLT — имя модуля вывода групп;
  PRIME v2 — внутреннее имя кодовой базы.
- **Р4 — дескрипторы типов в основном конфиге** (шаблон из nearest neighbors);
  LLM-редактор дескрипторов — абляция.
- **Р5 — состав арок E2 подтверждён** (лестница §7/E2 в v3-терминах).
- **Р6 — объём первой миграции: Фазы 0–1 + E1.** Уточнение семантики: в E1
  старый батч-механизм временно остаётся только поставщиком данных мутатору
  (роль D_mut, смещение допустимо); все решения о кандидатах (fitness, селекция,
  carryover) — исключительно с D_select. Полная замена пула — Фаза 2.
- **Р7 — fit/heldout = 70/30 по user_id**, сид в конфиге, user-disjoint;
  примеры юзера целиком в одной половине.
- **Р8 — легаси v2 заменяется, дефолт = v3:** агрегация median (majority —
  абляция), κ только в `v1_weighted`, fit кластеров label-free; full-проекция —
  только диагностический отчёт (ANOVA rating-статистик по кластерам).
- **Р9 — размеры и мощность:** n_min=40 (K ≤ |D_select|/40); полный ран
  |D_select|=400, |D_anchor|=100, |D_mut|=35; capped E1 — 200/50/30;
  D_anchor ⊂ heldout, дизъюнктен с D_select; `min_reviews_for_fit=3`
  (юзеры с меньшим числом отзывов не участвуют в fit k-means, но назначаются).
- **Р10 — порог прокси-гейта не фиксируется до данных:** в E1 только
  логирование corr(CVaR_cluster, R_worst_val); порог выбирается на Фазе 4
  по первым ранам.

Решения Р11–Р15 — по итогам внешнего ревью (триаж «блок A»):

- **Р11 — критерий E1 ужесточён:** primary — официальный R_worst_val («И», не
  «ИЛИ»); выигрыш только по суррогату CVaR_cluster = weak-go (ремонт прокси,
  не успех).
- **Р12 — E0 обязателен до E1** (один инференс val; primary gate =
  permutation Kruskal–Wallis, LOO Spearman только диагностика; см. OBSERVATIONS P1);
  смета бюджета — в §7; вызовы val/прокси-гейта/audit входят в B.
- **Р13 — random-clusters контроль обязателен** в абляциях (фальсифицирующая
  арка групповой гипотезы).
- **Р14 — MIPROv2 (DSPy) добавлен** в E3 и E9.
- **Р15 — пакет протокольных ужесточений:** D_audit (nested-мера post-selection
  bias); anchor-гейт с CI/δ-допуском + счётчик отклонений; стратификация
  fit/heldout-разбиения; таблица информационного доступа + algorithm box в
  статью; арка inferred-vs-oracle на CivilComments; условное повышение
  структурного промпта до вклада при подтверждении абляцией.
