# RQ6 — Отбор: чинит ли перераспределение того же бюджета

## Вопрос

Если тот же самый размеченный бюджет валидации сконцентрировать на группах,
которые худшие уже для стартового промпта, восстанавливается ли способность
отбирать?

## Короткий ответ

Да. Это единственный положительный результат проекта. На пуле оптимизаторов все
12 групповых статистик меняют знак на положительный (средний сдвиг Spearman
+0.876), ошибка отбора падает 0.0600 → 0.0075 (≈8×), group-free правило на
сконцентрированной валидации даёт regret **0.0000**. Без единой дополнительной
метки. На Amazon category-shift regret 0.025 → 0.007.

Оперативная переменная — **куда потрачены примеры**, не «насколько групповое
правило». Метки нужны, чтобы решить где тратить; считать можно group-free
метрикой.

### Selection regret на S9-пуле (pool best = 0.6675)

| dev rule | uniform pick | regret | targeted pick | regret |
|----------|--------------|-------:|---------------|-------:|
| любая групповая статистика | `44_apo` | 0.0600 | **`42_prime`** | **0.0075** |
| worst-class (group-free) | `44_evoprompt_de` | 0.0225 | **`42_gpo`** | **0.0000** |
| global accuracy | `43_ape_k48` | 0.0375 | `42_prime` | 0.0075 |

Четыре следствия из отчёта:

1. Worst-group selection не сломан — сломана была равномерная аллокация.
2. Чувствительная поверхность F8 (k, τ, w) была артефактом шума: при точных
   per-group оценках 10/12 конфигураций выбирают один промпт.
3. Оперативная переменная — аллокация, не group-awareness правила. Лучший
   исход (regret 0) даёт **group-free** статистика на group-concentrated dev.
   Рецепт: метки решают куда тратить, считать можно дёшево без групп.
4. Под правильной аллокацией групповые правила берут `42_prime` (test 0.6600),
   0.0075 от оптимума пула — первый случай в расследовании, где group-robust
   selection ведёт себя как задумано.

## Вывод

Worst-group отбор при реалистичном бюджете — задача **аллокации измерения**.
Равномерное покрытие делает каждый worst-group критерий антикоррелированным с
его же целью; перераспределение того же бюджета на идентифицируемо-худшие
группы переворачивает знаки и режет regret в 8 раз. Это не заявлено ни в одной
известной нам работе по prompt optimization.

## Чего не хватает (три риска, все серьёзные)

1. **P0. Переселекция матрицы S9 на targeted dev из архивов методов.**
   Прямо измеряет, какая доля опубликованного числа каждого метода — артефакт
   аллокации. Один проход D_dev на промпт, тест уже есть.
2. **P1. Второй независимый draw валидации.** Целевые группы выбраны на том же
   split, что и оценка. Split-specific artifact не исключён (caveat в F9).
3. **P1. Абляция аллокации:** 2×225 / 3×150 / 4×112 / 9×50. Неизвестен перелом
   precision vs coverage. Риск: метод чинит seed-worst группы и ломает четвёртую
   — targeted dev этого не увидит. F9 это не тестирует.

Пока (2) и (3) не закрыты, формулировка в статье должна нести caveat про один
validation split и про seed-worst targeting.
